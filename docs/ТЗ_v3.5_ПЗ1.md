## 2. 🔴 БЛОКЕР — формула итогового времени хода

**Не менять формулу до ответа заказчика.**

Конфигурация из презентации: два перегона — 72 км/300 км/ч и 174 км/200 км/ч, разгон 2 мин + торможение 1 мин на перегон.

**Текущий расчёт (предположительно верный инженерно):**
```
перегон_1 = 72/300*60 + 3  = 17.4 мин  → экран показывает 00:17
перегон_2 = 174/200*60 + 3 = 55.2 мин  → экран показывает 00:55
ИТОГО = 17.4 + 55.2 = 72.6 мин ≈ 01:13   (текущее значение на экране)
```

**Заказчик считает это неверным и указывает результат 01:18.** Комментарий на слайде: «Сумма времени в пути + 3 × количество перегонов».

**Проверка гипотезы:** если взять уже отображённые по-строчные значения (00:17 + 00:55 = 72 мин, где разгон/торможение уже учтены построчно) и прибавить **ещё раз** 3×2=6 мин сверху — получается 78 мин = 01:18. Совпадает с числом заказчика.

**Вывод:** буквальное прочтение формулы заказчика приводит к двойному учёту разгона/торможения на каждом перегоне. Это может быть:
(а) заказчик неверно прочитал экран (принял уже-с-разгоном значения за «чистое время»), или
(б) осознанное требование — разгон/торможение должны действительно считаться дважды (например, если методология подразумевает разгон в начале пути и торможение в конце отдельно от межстанционных потерь).

**Действие:** не трогать код. Показать заказчику именно эту раскладку (что 78 мин получается только при двойном счёте) и получить явное подтверждение, какой вариант верен. До ответа — тесты на текущую формулу (01:13 для этой конфигурации) не менять.

## 6. Новая формула — стоимость проезда личного автомобиля

**Существующая (для каждой корреспонденции):** не вводится студентом, **вычисляется** из данных экрана «Прочие параметры» (обеих станций корреспонденции — уточнить у заказчика, если города разные, чьи параметры брать, см. допущение ниже):

```
стоимость_существующая =
  ( Расход_100км × Цена_АИ92 × (Длина_трассы_ВСМ / 100)
    + ОСАГО_и_ТО_за_км × Длина_трассы_ВСМ )
  / 1.3
  + 200
```

- `1.3` — наполняемость автомобиля (то же значение, что и в других расчётах, поле из «Прочих параметров»)
- `200` — фиксированная надбавка, природа не пояснена заказчиком (вероятно, городские издержки — парковка и т.п.). 🧩 Не пояснять в UI/PDF происхождение числа, пока заказчик не уточнит.
- `Длина_трассы_ВСМ` — общая длина трассы (не длина именно этой корреспонденции, если корреспонденций несколько — **уточнить у заказчика**, это явно не указано на слайде и может быть ошибкой формулировки)

🔴 **Отдельно уточнить у заказчика:** если на линии больше 2 станций и несколько корреспонденций — берётся общая длина всей трассы ВСМ или длина конкретного участка (перегона) между станциями этой корреспонденции? Формула на слайде явно говорит «Длина трассы ВСМ», но по смыслу (стоимость поездки *по этому маршруту*) логичнее длина участка. Не решать самостоятельно — эта неоднозначность влияет на все корреспонденции, кроме случая с 2 станциями.

**Прогнозная (для каждой корреспонденции):** поле помечено заказчиком как «считается из предыдущего этапа» — требует уточнения, что именно это значит (см. блокер ниже).

🔴 **Дополнительная неопределённость:** на слайде презентации есть третья аннотация — «По умолчанию существующая + 200» — её точная привязка к полю визуально неоднозначна (стрелка пересекается с другими, могла указывать на «Самолёт»/«Пригородный поезд», а не на личный автомобиль). **Уточнить у заказчика**, к какому полю относится это правило, прежде чем реализовывать.

## 8. Перенесено из проверки скриншотов от 20.08 — не закрыто

### П-13. 🔴 Крупное — 13 итоговых показателей ПЗ1, похоже, не связаны с расчётами

В присланном `wet-report.pdf` раздел «Технико-экономические показатели» содержит значения, не похожие на результат вычислений: «Максимальная скорость 245», «Ширина колеи 121», «Затраты на строительство 23», «**Ограничения и допущения 543**» — последнее по смыслу текстовое поле (описание рисков/допущений проекта), но хранит число. **Похоже, что 13 итоговых показателей сейчас — свободный ручной ввод, не вычисляемые поля.** Это самый крупный оставшийся объём работы по ПЗ1: финальный экран должен получать показатели из модели (длина трассы, время хода, пассажиропоток, билетная выручка = поток × средняя цена билета, и т.д.), а не позволять произвольный ввод. Часть показателей (например, «Ограничения и допущения») по своей природе текстовые, не числовые — форма ввода должна это отражать.

**Не бралось в работу заказчиком явно** — но стоит поднять вопрос до того, как он это заметит сам, потому что объём немаленький.
