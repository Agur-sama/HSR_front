### Сегмент и «радиус» — важное уточнение (я раньше объяснял это неверно)

Поле называется «Радиус между точками» (по прямому требованию заказчика), измеряется в **метрах**, но по сути хранит **стрелу прогиба** (насколько дуга отклонена от прямой), не настоящий геометрический радиус кривизны. Это осознанное и задокументированное расхождение с реальной геометрией (радиус и стрела — разные величины), заказчик его принял по своему прямому указанию. **В коде переменную называть нейтрально `bendM`, не `radiusM`** — чтобы будущий переход на настоящий радиус не потребовал переименования с изменением смысла.

Норматив методички (радиус кривой ≥10000м при 400км/ч и т.д.) к этому полю **не применяется напрямую** — тема настоящих радиусов кривизны заказчиком сознательно отложена как сложная.

**Метод расчёта длины — геодезический, не плоский.** Хорда между соседними вершинами — по гаверсинусу (сфера, R=6371 км), не по декартовой разнице координат и не в Web Mercator напрямую: на широтах России (55–60°) Web Mercator даёт ошибку в десятки процентов на дистанциях в сотни километров, и это молча исказит длину трассы, а через неё — время хода и все расчёты, которые от неё зависят (стоимость проезда личного авто, технико-экономические показатели). Дуга/стрела — в локальной касательной плоскости (ENU), центр — середина хорды сегмента, обратное преобразование в `lon/lat` для отрисовки. Контрольный тест — реальная пара городов варианта, сверить с известным расстоянием.

### Структура шагов — актуальная (страница на тему, не на корреспонденцию)

Прежние формулы (`3+2×C(n,2)`, затем `4+7×C(n,2)`) **обе недействительны** — вторая давала до 46 экранов при 4 станциях, заказчик прямо отклонил такую компоновку. Актуальная модель: **страница на тему, все корреспонденции внутри одной страницы**, число шагов ≈10–12 и **не зависит** от числа станций.

1. **Паспорт + вариант** — учебная группа (без валидации), вариант (список из 6, формат «Вариант N — Город1, Город2»)
2. **Оверлей «Цель ПЗ1»** при первом входе — 4 задачи со слайда методички (текст пришлёт заказчик)
3. **Карта** — станции + линия трассы (2 набора точек, см. предупреждение выше), режимы «Просмотр / Станция / Линия трассы / Центр» одной строкой; привязка станции к региону (список с поиском, справочник субъектов РФ статикой)
4. **Время хода ВСМ** (новый экран после карты, БЕЗ карты на этом экране) — по каждому перегону: расстояние, средняя скорость (ввод), разгон/торможение (2 и 1 мин, нередактируемые, отдельными столбцами), итоговое время ЧЧ:ММ. Формула `t = S/V + 2 + 1` мин на перегон — **корректна**, не переделывать.
5. **Характеристики регионов** — по каждому региону (не по корреспонденции): ВРП (существ./прогноз, ячейка пополам), население (существ./прогноз), средняя зарплата, `kGdpFlow` (подпись в UI — «Коэффициент влияния ВВП на пассажиропоток», расчёт по-прежнему региональный). Общее поле: индуцированный спрос %. Хранится один раз на регион, в корреспонденцию подставляется по ссылке.
6. **Время в пути** — таблицы по **всем** корреспонденциям на одной странице, 4 строки (время до вокзала, ожидание, чистое время — для ВСМ приходит из шага 4, остальное — время от вокзала до города) + ИТОГО, формат ЧЧ:ММ. Личное авто: только чистое время, остальное `0:00` заблокировано. ВСМ: существующее = 0.
7. **Коэффициент дискомфорта** — **одна таблица** (не две) на корреспонденцию, ячейка пополам (существующее/прогнозное) — все корреспонденции на одной странице. Предзаполнение 108 значений, агрегат = среднее строк 1–8 (строка 9 не входит), вычисляемое поле.
8. **Прочие параметры** — **по станциям** (2–4 таблицы), не по корреспонденциям. Поля: стоимость проезда по городу (одно поле, не два), наполняемость авто (деф. 1,3), рабочие часы/год (деф. 1973), бензин (деф. 55 руб/л), расход (деф. 11 л/100км), ОСАГО+ТО (деф. 1,75 руб/км). При расчёте корреспонденции город 1/2 берутся из таблиц соответствующих станций. **Порядок именно здесь (не после «Частоты+Стоимости»!) — не косметика:** формула стоимости личного авто (см. ниже) использует эти поля, если экран стоимости идёт раньше — расчёт невозможен. **Реализовано (ТЗ v3.6 T-2):** «Прочие параметры» — позиция 06, «Частота+Стоимость» — 07. Порядок задаётся списком `pz1StepIds` в `model.ts` и больше нигде; счётчик «N из 10» считается из его длины.
9. **Частота сообщения + Стоимость проезда** — объединены на одной странице, все корреспонденции. Рейсов/сутки и руб./пасс. ВСМ существующая = 0 (обе). Личное авто существующая стоимость — **вычисляется**, не вводится (см. формулу ниже). Частота: личное авто заблокировано.
10. **Пассажиропоток и модель** — на каждую корреспонденцию: расчёт существующего годового потока (`365×рейсы×вместимость×заполняемость`, коэффициенты заполняемости предзаполнены), прогонка модели (см. `examples/pz1-passenger-flow.md`), накопительная диаграмма (`recharts`). В UI термин — «имитационная модель» (не «гравитационная» — то внутреннее).
11. **Итог** — сводка по всем корреспонденциям + 13 итоговых показателей (`data-entry-hint`), кнопка «Назад» (живой пересчёт при правке), экспорт PDF/JSON.

**Практический вывод для реализации:** все таблицы с видами транспорта/корреспонденциями — один переиспользуемый компонент с конфигом (виды транспорта × 2 ячейки × подписи × блокировки), не 6 независимых вёрсток.

### 🔴 БЛОКЕР — формула итогового времени хода (не менять код до ответа заказчика)

На конкретном примере (72км/300км/ч + 174км/200км/ч, разгон 2мин+торможение 1мин на перегон) текущий расчёт даёт 01:13 — построчно верно инженерно (`t=S/V+3` на каждый перегон, посчитано верно). Заказчик считает правильным **01:18**, что получается, только если прибавить `3×количество_перегонов` **ещё раз поверх** уже посчитанных построчных значений — то есть двойной учёт разгона/торможения. Не ясно, это ошибка чтения экрана заказчиком (принял уже-с-надбавкой построчные значения за «чистое время») или осознанное требование методологии. **Действие: показать заказчику именно эту раскладку, дождаться явного ответа, не трогать формулу.** (Это отдельный, более свежий вопрос, чем ранее закрытый в этом файле «баг оказался дисплейным» — тот разбирал другую конфигурацию и другую жалобу, про плитки «Разгон/Торможение» на итоговом экране; этот — про саму формулу суммы.)

### Формула — стоимость проезда на личном авто (существующая, вычисляется, не вводится)

```
стоимость_существующая = (Расход_100км × Цена_АИ92 × Длина_ВСМ/100 + ОСАГО_ТО_за_км × Длина_ВСМ) / 1,3 + 200
```
`1,3` — наполняемость авто (то же поле, что и везде). `200` — фиксированная надбавка, природа не пояснена заказчиком, **не объяснять в UI/PDF**, пока не уточнит.

**Три открытых вопроса, не додумывать:**
1. У корреспонденции две станции, у каждой свои «Прочие параметры» (см. шаг 8 выше, теперь по станциям) — чьи данные брать для этой формулы, если параметры городов разные?
2. `Длина_ВСМ` — общая длина всей трассы, или длина именно этого перегона/корреспонденции? На слайде буквально «длина трассы ВСМ», но по смыслу поездки логичнее длина конкретного участка. Существенно при >2 станций.
3. Отдельная аннотация «по умолчанию существующая + 200» на слайде заказчика — неясно, к какому полю относится (стрелка визуально пересекается с несколькими полями, могла указывать на Самолёт/Пригородный, не на личный авто).

### Лок вместимости ВСМ

«Вместимость ТС существующая» для строки ВСМ на экране «Годовой пассажиропоток» — залочена на `0`, как уже сделано для частоты/стоимости ВСМ (линии ещё не существует). Сейчас требует заполнения и блокирует переход — это баг, не отсутствующая фича.

### 🔴 КРУПНАЯ НАХОДКА — 13 итоговых показателей похоже не связаны с расчётами

Судя по реальному PDF-отчёту: «Максимальная скорость 245», «Затраты на строительство 23», «Ограничения и допущения 543» (текстовое по смыслу поле хранит число), «Билетная выручка 54» при «Общий пассажиропоток 0» (выручка положительная при нулевом потоке — невозможно, если поле производное). **Похоже, что сейчас это свободный ручной ввод, не вычисляемые поля** — прямое нарушение принципа «живого итога» (`ФТ-20/21`). Это самый крупный оставшийся кусок работы по ПЗ1: нужно спроектировать, какой из 13 показателей из чего считается (длина трассы → из карты, время хода → из шага 4, пассажиропоток → из модели прогноза, билетная выручка = поток × средняя цена билета и т.д.), какие показатели по природе текстовые (не числовые — «Ограничения и допущения» описание, не число). **Не начинать без отдельного плана** — не переиспользовать существующие поля ввода молча.

### Семантика исключения вида транспорта — уточнена заказчиком 31.08 (ТЗ v3.6 T-1)

Исключённый вид **остаётся в расчёте с нулевыми значениями**, а не выбрасывается из него. Дословно: «если мы вдруг его удаляем, то для модели это просто все нули». Он сохраняет строку в результате модели (нули по прямому, гравитационному и индуцированному захвату) и входит в нормализацию с нулевым весом.

Прежнее допущение о «локальной нормализации внутри пары» — перераспределении долей исключённого вида между оставшимися — **отменено, не реализовывать**. Технически это значит: массив входов модели строится по всем шести видам, а не по активным; исключённые помечаются флагом `excluded` и не проходят проверок на положительность стоимости и времени (их поля студент не заполнял).

Исключение действует **в пределах одной корреспонденции**. ВСМ неудаляем. Состояние живёт в `correspondenceTables[pairKey].activeModes` и сохраняется в JSON-мосте.

## ПЗ2 — Профиль и план трассы
1. `scheme-reader` — продольный профиль, проверка уклона ≤24‰, поиск вертикальных кривых, `R_в = Vmax² / (3,6² · a_в)`

## ПЗ3 — Выбор ВСП и ИССО
На каждый из двух участков (10–30 км, выбираются из линии ПЗ1). **Подтверждено текстом методички:** скорость участка берётся из исходных данных ПЗ1 («на основе исходных данных задания 1 с учётом трассировки»), не из ПЗ2 — мост ПЗ1 → ПЗ3 напрямую.
1. `data-entry` — общая характеристика (протяжённость, рельеф, грунты, климат, скорость — пред-заполняется из ПЗ1)
2. `data-entry`, 7 категорий — назначение нижнего строения пути (земляное полотно, мосты, эстакады, путепроводы, тоннели, биопереходы, шумозащита)
3. `data-entry` + текстовое обоснование — выбор ВСП (балласт/безбалласт)
4. `data-entry` (условный) — характеристика ИССО, если участок требует сооружения
5. `data-entry-hint`, 12 строк-статей расходов (подготовка территории, земляное полотно, 3 вида ИССО, 2 вида ВСП, 3 объекта трансп. хозяйства, 2 экологических мероприятия) — количество × цена за ед. (справочная) → стоимость, итог на участок и на 1 км
6. `control-questions`

4. `calculator` — пропускная способность (ПАБ / АБ,АЛСО,РБ), объём перевозок `A = 2·N·n_пасс·α_зап`

## ПЗ6 — Стойла в депо
**Подтверждено:** автономный модуль, как ПЗ4/ПЗ5/ПЗ8 — своя 10-вариантная таблица (длина участка `l`, число пар поездов `N`) полностью покрывает нужные входы, мост из ПЗ1/ПЗ2/ПЗ7 не требуется. Убрано из графа зависимостей.
1. `interactive-table-variant` — длина участка, число пар поездов/сут
2. `calculator`, каскад — годовой пробег `S`, ревизии R5→R1 (каждая формула вычитает предыдущие), инспекции IS530→IS510, ТО N и L (та же каскадная логика)
3. `table-calculator-hybrid` — стойла по видам обслуживания, строка «Итого»

## ПЗ7 — Набор остановок + потребный парк
**Часть 1:**
1. `interactive-table-matrix` — шахматка пассажиропотоков, размер **динамический** (2–4 станции по факту созданных в ПЗ1: А/Г обязательны, Б/В опционально) — пример методички на 5 станциях (А–Д) чисто иллюстративный, не привязан к реальному числу станций команды
2. `interactive-table-optimizer` — редактируемое число поездов по маршрутам (без остановок / 1 остановка Б / В / Г / 2 остановки … / все остановки), живой пересчёт показателей с цветовой подсказкой
3. `control-questions` × 5 под-вопросов вокруг того же состояния оптимизатора: анализ матрицы → влияние остановок на время в пути → анализ показателей → минимизация пассажиро-часов → минимизация размеров движения

**Часть 2:**
4. `schedule-graph` — график движения поездов (нитки), курсор по времени считает пересечения → потребный парк
5. Механика «увязки поездов по станциям оборота» — не финализирована, см. open-questions. Визуально проверено: методичка даёт готовый пример «график до / после увязки» плюс таблицу потребного числа путей оборота по станциям — похоже на задачу распределения прибывающих/отправляющихся поездов по ограниченному числу путей оборота, а не на свободную линковку ниток кликами.
6. `calculator` — потребный парк подвижного состава

## ПЗ8 — Обслуживание пассажиров (опрос)
**Подтверждено:** в содержании методички есть отдельный этап «Проведение онлайн-опроса» — это реальный полевой опрос, не симуляция внутри команды. Это создаёт архитектурное трение с «нет бэкенда»: наше приложение не может само хостить сбор ответов от посторонних людей. **Рабочая трактовка (наше архитектурное решение, не факт из методички):** `survey-constructor` помогает спроектировать структуру анкеты, реальный опрос студенты проводят во внешнем инструменте (Яндекс.Формы/Google Forms), а наше приложение принимает уже собранные ответы для анализа.
1. `survey-constructor` — конструктор анкеты (типы вопросов, варианты ответов), экспорт структуры для внешнего инструмента
2. `data-entry` — импорт/ручной ввод собранных ответов
3. `calculator` — анализ ответов, визуализация
4. `control-questions` — выводы
