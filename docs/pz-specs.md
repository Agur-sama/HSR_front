# Спецификации по каждому ПЗ

См. также: [architecture.md](./architecture.md) для определения `kind` · [open-questions.md](./open-questions.md)

Сверено построчно с методичками (не с пересказом), формулы и структуры выборочно перепроверены напрямую по PDF. Этот файл будет меняться чаще остальных по мере кодирования модулей — уточнения по конкретному ПЗ вносить сюда точечно.

## ПЗ1 — Технико-экономическое обоснование

**Итоговое число шагов фазы «задание» — переменное:** `3 + 2×C(n,2)`, где n — число станций (2..4), C(n,2) — число корреспонденций. Диапазон: **5 шагов** (2 станции) … **15 шагов** (4 станции). См. таблицу:

| Станций | Корреспонденций | Итого шагов |
|---|---|---|
| 2 | 1 | 5 |
| 3 | 3 | 9 |
| 4 | 6 | 15 |

Показать команде оценку числа шагов сразу после расстановки станций (до входа в шаг 3) — иначе решение «сколько промежуточных ставить» принимается вслепую, а разброс объёма работы кратный.

1. `drag-drop-map` — станции + линия трассы. **Два независимых набора точек, не путать (частая ошибка):**

   **Станции** (метки А/Б/В/Г) — количество ЖЁСТКО ограничено: ровно 2 терминальные (А, Г) + максимум 2 промежуточные (Б, В). Итого от 2 до 4 станций. Семантические, с подписями и типом. UI не даёт поставить 3-ю промежуточную.

   **Вершины линии трассы** (waypoints) — количество НЕ ограничено (0..∞). Студент ставит сколько нужно, чтобы обвести воду, горы, повторить реальный коридор. Без подписей, без лимита. Линия рисуется как polyline ПО ЭТИМ вершинам.

   **Ключевое правило:** `routeLine` — самостоятельный редактируемый массив вершин, он НЕ генерируется автоматически из станций. Соединять станции прямыми — это баг (тогда географию нечем обходить). Станции и линия хранятся раздельно; линия визуально проходит через/около станций, но геометрически задаётся своими вершинами.

   Механика ввода — два режима (как инструменты Яндекс.Карт «метка» и «линия»):
   - режим «Станция»: клик ставит следующую станцию (валидация лимита), drag двигает
   - режим «Линия трассы»: клик добавляет вершину в конец, drag двигает вершину, можно вставить вершину между двумя существующими и удалить вершину — стандартное редактирование polyline
   - ручной ввод координат валидируется до передачи в карту: широта `-90…90`, долгота `-180…180`; некорректное значение показывает ошибку, но не роняет приложение
   - названия включённых станций уникальны; дубль — blocking-валидация
   - рядом с общей длиной показываются расстояния между соседними станциями вдоль фактической линии трассы
   - (опционально, отдельный инструмент) «Регион» — полигоны прохождения, БЕЗ лимита; нужны ли — см. open-questions

   **Кривые сегментов:**
   Трасса не должна быть набором чистых прямых. Между соседними точками задаётся параметр кривизны сегмента; в текущей реализации студент вводит стрелу прогиба, а радиус и длина дуги вычисляются производно. Вопрос перехода на ввод радиуса не закрыт — см. `open-questions.md` и T-11 в ТЗ v3.0.
   - на выходе нужны: **общая длина трассы**, длина по каждому участку, параметры кривых (радиус, длина дуги)
   - ВСМ-линия рисуется **красным** и лежит **поверх** остальных слоёв карты
   - `routeLine` перестаёт быть плоским `Array<[number, number]>` — каждый сегмент несёт свой радиус:
     ```ts
     routeSegments: Array<{
       from: [number, number];
       to: [number, number];
       radius: number | null;   // null = прямая вставка
       lengthKm: number;        // вычисляется
     }>;
     totalLengthKm: number;     // сумма по сегментам
     ```
   - **Потенциальное усиление связи ПЗ1 → ПЗ2:** радиусы кривых — ровно то, что анализирует ПЗ2 (проверка радиуса на соответствие Vmax). Возможно, «слабое» ребро становится реальным переносом данных. **Не подтверждено** — вынесено в open-questions.

2. `interactive-table-matrix` — авто-генерация корреспонденций из станций. Определяет, сколько раз повторятся шаги 3 и 4 ниже. **Показать оценку объёма** («у вас N корреспонденций → M шагов впереди») сразу на этом экране, до входа в шаг 3.

3. `data-entry` — потребительские свойства, **повторяется на каждую корреспонденцию** из шага 2 (А-Б, А-В, А-Г, Б-В, Б-Г, В-Г при 4 станциях). В каждом наборе: время в пути, частота сообщения, средняя стоимость проезда — по видам транспорта.
   - **Удаление столбца:** если между конкретной парой станций какого-то вида транспорта не существует (например, нет прямого авиасообщения) — столбец удаляется из таблицы этой корреспонденции. Столбец ВСМ неудаляем и всегда присутствует.
   - **Коэффициент дискомфорта:** отдельная входная таблица на весь модуль, 9 критериев × 6 видов транспорта, диапазон 0…1; 0 = комфортно, 1 = дискомфортно, цветовая шкала зелёный→красный.
   - Объём заметно вырос относительно первоначальной оценки — учитывать при планировании.
4. `data-entry` + `calculator` — прогноз пассажиропотока: формула общего роста рынка + распределение по 6 видам транспорта через гравитационную модель, с накопительной диаграммой результата.
5. `data-entry-hint` — 13 итоговых показателей (протяжённость, Vmax, ширина колеи, станции, время в пути, годовой пассажиропоток, размеры движения по формулам N_сут/A_max, потребный парк по I_ВСМ/T_об/M, затраты на строительство и подвижной состав со справочными диапазонами цен, билетная выручка на 0/5/10/15/20 год)

## ПЗ2 — Профиль и план трассы
1. `scheme-reader` — продольный профиль, проверка уклона ≤24‰, поиск вертикальных кривых, `R_в = Vmax² / (3,6² · a_в)`
2. `scheme-reader` — план трассы, радиус кривой, возвышение рельса `h ≤ Vmax²/(3,6²R) − a_н·S/g`
3. `calculator` — итоговый экран: участок/мин.радиус/макс.уклон/радиус верт.кривой → выбор лимитирующего условия → итоговая Vmax

## ПЗ3 — Выбор ВСП и ИССО
На каждый из двух участков (10–30 км, выбираются из линии ПЗ1). **Подтверждено текстом методички:** скорость участка берётся из исходных данных ПЗ1 («на основе исходных данных задания 1 с учётом трассировки»), не из ПЗ2 — мост ПЗ1 → ПЗ3 напрямую.
1. `data-entry` — общая характеристика (протяжённость, рельеф, грунты, климат, скорость — пред-заполняется из ПЗ1)
2. `data-entry`, 7 категорий — назначение нижнего строения пути (земляное полотно, мосты, эстакады, путепроводы, тоннели, биопереходы, шумозащита)
3. `data-entry` + текстовое обоснование — выбор ВСП (балласт/безбалласт)
4. `data-entry` (условный) — характеристика ИССО, если участок требует сооружения
5. `data-entry-hint`, 12 строк-статей расходов (подготовка территории, земляное полотно, 3 вида ИССО, 2 вида ВСП, 3 объекта трансп. хозяйства, 2 экологических мероприятия) — количество × цена за ед. (справочная) → стоимость, итог на участок и на 1 км
6. `control-questions`

## ПЗ4 — Напряжение плеч питания
Автономный модуль (не зависит от других ПЗ), но **не «только паспорт», как считалось раньше** — у него своя 10-вариантная таблица (S_КЗ, I_Л, I_П, φ_Л, φ_П, S_Н, u_K; U_Н фиксировано — 27,5 кВ, не варьируется).
1. `interactive-table-variant` — 10 вариантов
2. `calculator`, цепочка из 3 шагов, каждый использует переменные предыдущего:
   - `x_C = U_H² / S_КЗ`, `x_T = (u_K/100) · U_H²/S_H`
   - `ΔU_Л`, `ΔU_П` (с sin/фазовыми углами — формулы проверены на рендер через KaTeX)
   - `U_Л = U_H − ΔU_Л·10⁻³`, `U_П = U_H − ΔU_П·10⁻³`
3. `data-entry` — текстовые рекомендации

## ПЗ5 — Сигналы + пропускная способность
**Часть 1:**
1. `drag-drop-scheme` — 5 последовательных под-шагов ограждения на одной схеме (станция от перегона → приёмоотправочные пути → главные пути со стороны приёма → вытяжные/подъездные пути → бесстрелочные участки), затем нумерация маневровых светофоров
2. `control-questions`

**Часть 2:**
3. `interactive-table-variant` — 10 вариантов
4. `calculator` — пропускная способность (ПАБ / АБ,АЛСО,РБ), объём перевозок `A = 2·N·n_пасс·α_зап`
5. `control-questions`

## ПЗ6 — Стойла в депо
**Подтверждено:** автономный модуль, как ПЗ4/ПЗ5/ПЗ8 — своя 10-вариантная таблица (длина участка `l`, число пар поездов `N`) полностью покрывает нужные входы, мост из ПЗ1/ПЗ2/ПЗ7 не требуется. Убрано из графа зависимостей.
1. `interactive-table-variant` — длина участка, число пар поездов/сут
2. `calculator`, каскад — годовой пробег `S`, ревизии R5→R1 (каждая формула вычитает предыдущие), инспекции IS530→IS510, ТО N и L (та же каскадная логика)
3. `table-calculator-hybrid` — стойла по видам обслуживания, строка «Итого»

## ПЗ7 — Набор остановок + потребный парк
**Часть 1:**
1. `interactive-table-matrix` — шахматка пассажиропотоков, размер **динамический** (2–4 станции по факту созданных в ПЗ1: А/Г обязательны, Б/В опционально) — пример методички на 5 станциях (А–Д) чисто иллюстративный, не привязан к реальному числу станций команды
2. `interactive-table-optimizer` — редактируемое число поездов по маршрутам (без остановок / 1 остановка Б / В / Г / 2 остановки … / все остановки), живой пересчёт показателей с цветовой подсказкой
3. `control-questions` × 5 под-вопросов вокруг того же состояния оптимизатора: анализ матрицы → влияние остановок на время в пути → анализ показателей → минимизация пассажиро-часов → минимизация размеров движения

**Часть 2:**
4. `schedule-graph` — график движения поездов (нитки), курсор по времени считает пересечения → потребный парк
5. Механика «увязки поездов по станциям оборота» — не финализирована, см. open-questions. Визуально проверено: методичка даёт готовый пример «график до / после увязки» плюс таблицу потребного числа путей оборота по станциям — похоже на задачу распределения прибывающих/отправляющихся поездов по ограниченному числу путей оборота, а не на свободную линковку ниток кликами.
6. `calculator` — потребный парк подвижного состава

## ПЗ8 — Обслуживание пассажиров (опрос)
**Подтверждено:** в содержании методички есть отдельный этап «Проведение онлайн-опроса» — это реальный полевой опрос, не симуляция внутри команды. Это создаёт архитектурное трение с «нет бэкенда»: наше приложение не может само хостить сбор ответов от посторонних людей. **Рабочая трактовка (наше архитектурное решение, не факт из методички):** `survey-constructor` помогает спроектировать структуру анкеты, реальный опрос студенты проводят во внешнем инструменте (Яндекс.Формы/Google Forms), а наше приложение принимает уже собранные ответы для анализа.
1. `survey-constructor` — конструктор анкеты (типы вопросов, варианты ответов), экспорт структуры для внешнего инструмента
2. `data-entry` — импорт/ручной ввод собранных ответов
3. `calculator` — анализ ответов, визуализация
4. `control-questions` — выводы
