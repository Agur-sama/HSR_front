# Архитектура — техническое ядро

См. также: [design-system.md](./design-system.md) · [pz-specs.md](./pz-specs.md) · [open-questions.md](./open-questions.md)

## Стек

- React 19 + TypeScript + Vite. Тесты — Vitest.
- Стилизация — обычный CSS с custom properties. **Tailwind и Framer Motion не подключены.** Добавление — отдельное решение, фиксировать здесь явно.
- **Бэкенда нет.** Никакого Django/Postgres/Docker-compose. Причина: преподаватель проверяет работы вручную по PDF, аккаунты и роли не нужны. Деплой — статическая сборка `vite build` за одним Caddy/Nginx.
- Пакеты к подключению: `katex` (формулы — рендер проверен вручную через CDN, рисков с Vite не ожидается), `@react-pdf/renderer` (PDF-отчёт). Карта ПЗ1 реализуется без Leaflet/MapLibre: собственный React-слой поверх raster tiles OpenStreetMap.

## Структура репозитория

```
src/
  app/                  — корневая оболочка, точка входа
  modules/
    pz1/
      steps/            — компоненты шагов конкретного ПЗ
      variants.ts        — статические пресеты вариантов (если есть у ПЗ)
      slides.ts           — типизированный контент теории
      types.ts             — PzNResult и внутренние типы модуля
      index.tsx
    pz2/ … pz8/           — та же структура
  shared/
    ui/                    — переиспользуемые компоненты (кнопки, инпуты, табличные примитивы, прогресс-трасса)
    lib/                     — чистые расчётные функции, без React
    hooks/
    types/
  bridge/
    schema.ts               — Passport, BridgeSchema, PzNResult union
    context.tsx               — ModuleStateProvider (см. «Состояние» ниже)
    io.ts                       — экспорт/импорт JSON моста
  pdf/
    templates/
    render.ts
docs/
  architecture.md
  design-system.md
  pz-specs.md
  open-questions.md
  examples/
    pz1.md … pz8.md          — тестовые фикстуры из методичек
```

**Правило:** код одного ПЗ не импортирует код другого ПЗ напрямую. Переиспользуемая логика/UI выносится в `shared/`.

## Состояние приложения

- Локальное состояние одного шага — `useState`/`useReducer` внутри компонента шага.
- Состояние модуля целиком (массив шагов, текущий шаг, введённые данные до экспорта в мост) — один React Context на модуль (`ModuleStateProvider` в `bridge/context.tsx`), инициализируется из моста при входе в модуль.
- Мост — обычный объект/файл (`bridge/schema.ts` + `bridge/io.ts`), не React state, не завязан на рендер-цикл. Модуль читает его на входе (pre-fill) и пишет на выходе (экспорт результата).
- Глобальный state-manager (Redux/Zustand/XState) **не используется** без явного пересмотра этого документа. Если конкретный модуль (например, ПЗ7 с несколькими синхронными виджетами — шахматка + оптимизатор + график) не тянет на Context — это отдельное точечное решение по этому модулю, а не пересмотр архитектуры всего приложения.

## Запрещено

- Хранить бизнес-логику/формулы внутри JSX или компонентов — только в `shared/lib`, с тестом рядом.
- Использовать `any`. Если тип неизвестен на момент разбора методички — `unknown` и явный `// TODO: уточнить по методичке`, не заглушка `any`.
- Хранить состояние нескольких шагов модуля в одном неструктурированном `useState`-объекте — использовать типизированный Context.
- Импортировать код одного ПЗ в другой напрямую.
- Добавлять глобальный state-manager без явного решения, зафиксированного в этом файле.
- Предлагать бэкенд/БД/авторизацию/роли — уже решено, что их нет; это самый частый срыв у агентов на таком проекте.

## Canvas UI — ограничения под iSpring iframe

- Web Object в iSpring — **прямоугольная форма фиксированного размера**, автор курса растягивает её вручную в редакторе (либо открывает в отдельном окне браузера с явно заданными размерами). Мы не управляем итоговым размером контейнера программно.
- Закладывать разумный минимальный размер (ориентир — 16:9 от ~960×540) и деградацию вёрстки при более тесных пропорциях, не только `overflow-hidden` в расчёте на «как получится».
- iframe кросс-доменный → `postMessage` единственный легальный канал наружу. Поддержка авто-resize плеером iSpring через `postMessage`/`ResizeObserver` **не подтверждена** — риск, `overflow-hidden` — надёжный минимальный вариант без внешней поддержки.
- Никаких форм регистрации/логина, глобальных футеров, тяжёлых хедеров. Компактная вёрстка, внутренние списки скроллятся изолированно (`overflow-y: auto`), без двойного скролла.
- Роли пользователей не проектируются — распределение ролей внутри команды происходит вне приложения, даже если упомянуто в методичке ПЗ1.

## Модель модуля (оболочка)

Единый жизненный цикл для всех 8 модулей:

```
интро (паспорт / вариант / импорт JSON)
  → теория (интро-проход + переоткрываемая панель поверх задания)
  → задание (массив шагов — не один слот)
  → итог (экспорт в мост + PDF)
```

Фаза «задание» — массив шагов, потому что методички разнотипны: ПЗ5 — два независимых блока в одном модуле, ПЗ1 — многошаговый с повтором расчёта на каждую корреспонденцию, ПЗ7 — два блока со своими под-шагами.

## Таксономия типов шага (`kind`)

Выведена из разбора всех 8 методичек, каждый тип прототипирован и визуально проверен. Примеры конкретных ПЗ — см. [pz-specs.md](./pz-specs.md).

| `kind` | Что это |
|---|---|
| `data-entry` | Открытые поля-бланки |
| `data-entry-hint` | Поле с постоянно видимой справочной подсказкой-диапазоном рядом (не placeholder, не tooltip) |
| `interactive-table-variant` | Параметр × N вариантов, назначенный вариант подсвечен (ПЗ4, ПЗ5, ПЗ6 — все три автономны именно благодаря этому шагу) |
| `interactive-table-matrix` | Симметричная шахматная таблица откуда/куда, диагональ заблокирована |
| `interactive-table-optimizer` | Таблица с редактируемыми значениями и живым пересчётом производных показателей + цветовая подсказка |
| `table-calculator-hybrid` | Таблица результатов, каждая строка — своя формула, есть строка «Итого» |
| `calculator` | Цепочка формул; шаг может использовать результат предыдущего шага внутри того же ПЗ |
| `drag-drop-map` | OpenStreetMap raster tiles без Leaflet/MapLibre, клик/drag станций, автопостроение линии |
| `drag-drop-scheme` | Готовая (не процедурная) SVG-подложка схемы + интерактивный слой с заранее размеченными валидными точками |
| `scheme-reader` | Готовая схема для чтения + производный расчёт (ничего не двигают) |
| `survey-constructor` | Конструктор анкеты + сбор/анализ ответов |
| `control-questions` | Короткие текстовые ответы на вопросы понимания |
| `schedule-graph` | График движения поездов, курсор для подсчёта пересечений |

**Важно про `drag-drop-scheme`:** реальные схемы станций (ПЗ5) — 4–5 параллельных путей с лестницей стрелочных переводов. Подтверждено визуальным просмотром PDF: сигналы добавляются послойно на одну и ту же схему, похоже на одну базовую топологию станции, не набор разных схем под варианты. Решение: не писать процедурный генератор произвольных станционных схем — вручную перерисовать 1–2 реальные схемы в SVG (тот же паттерн, что карта ПЗ1: готовая подложка + клики поверх), с заранее размеченными точками посадки по типу сигнала.

## JSON-мост между модулями

Единый накапливающийся файл, не отдельный на каждое ПЗ:

```ts
interface Passport {
  team: string;
  lineTitle: string;
  defaultVariant?: number;
  createdAt: string; // ISO 8601
}

interface BridgeSchema {
  schemaVersion: '1.0';
  passport: Passport;
  completed: Partial<{
    pz1: Pz1Result; pz2: Pz2Result; pz3: Pz3Result; pz4: Pz4Result;
    pz5: Pz5Result; pz6: Pz6Result; pz7: Pz7Result; pz8: Pz8Result;
  }>;
}
```

**Принцип:** мост только пред-заполняет входы следующего модуля, никогда не блокирует. Каждый ПЗ автономен — при отсутствии данных сверху работает ручной ввод/выбор варианта. Команды могут проходить ПЗ не по порядку.

### Граф зависимостей (проверено по методичкам — версия 2)

- ПЗ1 → ПЗ2: слабая/контекстная
- ПЗ1 → ПЗ3: **подтверждено** — скорость участка берётся из исходных данных ПЗ1 (дословно «на основе исходных данных задания 1»), не из ПЗ2
- ПЗ1 → ПЗ7: матрица корреспонденций, размер динамический по числу станций ПЗ1 (2–4)
- ПЗ4, ПЗ5, ПЗ6, ПЗ8: **автономны** — у каждого своя вариантная таблица (ПЗ4, ПЗ5, ПЗ6) или паспорт (ПЗ8) полностью покрывает нужные входы. Ранее предполагавшиеся рёбра ПЗ7→ПЗ6 и ПЗ1/ПЗ2→ПЗ6 **сняты** — подтверждено, что у ПЗ6 своя таблица (длина участка + число поездов), мост не требуется

## Модель варианта задания

- `passport.defaultVariant?` — если преподаватель называет один номер на весь семестр
- Свой `variants.ts` со статическими пресетами в модулях, где методичка задаёт вариантный набор — подтверждено для ПЗ1 (6 направлений), ПЗ5 и ПЗ6 (единый формат таблицы, 10 вариантов)
- Не универсально для всех 8 — где вариантов нет, ручной ввод/данные из предыдущего модуля
- Модуль может переопределить `defaultVariant`, если у него своя нумерация

## PDF-отчёт

Собирается на клиенте (`@react-pdf/renderer`), студент видит по завершении, скачивает и сдаёт вручную. Никакой БД на бэкенде.

**Гранулярность:** отдельный PDF на каждое ПЗ (кнопка на экране «Итог») + опциональная сборка всех в один комбинированный отчёт.

**Архитектура:** `generatePzReport(pzId, result, passport)` — одна функция на ПЗ; `generateCombinedReport(bridge)` вызывает её для каждого заполненного `completed.pzN` и склеивает в один `<Document>` — один шаблон, не два рендер-пути.

**Три категории контента:**
1. Числа/текст — рендерятся напрямую, без сложностей
2. Формулы — `@react-pdf/renderer` не рендерит KaTeX нативно. Рендерить в PNG на клиенте (offscreen canvas), сохранять как часть результата шага. Момент рендера (при завершении шага vs при экспорте) — см. open-questions
3. Визуальные шаги (карта, схема) — каждый визуальный `kind` обязан отдавать `previewImage: string` (base64 PNG) как часть результата шага — контракт зафиксировать до кодирования ПЗ5

**Черновая структура одного PZ-отчёта:** титул (линия, команда, ПЗ, вариант, дата) → секция на каждый шаг → контрольные вопросы отдельным блоком в конце.

## Тестовая стратегия

**Тестируем:**
- все расчётные функции в `shared/lib` — на примере из `docs/examples/pzN.md`
- парсинг и валидацию bridge (`bridge/schema.ts`, `bridge/io.ts`)
- миграции `schemaVersion`
- генерацию PDF — структурно (правильные секции/данные попали в документ), не пиксель-в-пиксель
- валидаторы вариантов (`variants.ts`)

**Не тестируем:** CSS, анимации, точную вёрстку.
