## 4. 🔴 БАГ-ЛИСТ ПЗ-1 (обратная связь преподавателя 29.07.2026)

### Уровень 1 — критичные (ломают прохождение)

**T-01. 🔴 Краш при ручном вводе координаты станции (долгота 111).**
При попытке ввести долготу вручную приложение падает.
- Диагноз (гипотеза): необработанное исключение при построении геометрии/проекции. Возможно — в расчёте дуги или ENU-преобразовании (см. §5.3).
- Требуется: (а) найти и устранить причину падения на конкретном вводе; (б) **обернуть все геометрические расчёты в защиту** — единичный некорректный ввод не должен ронять модуль. Показать пользователю сообщение об ошибке ввода, а не белый экран.
- Тест: ввод долготы 111 (и граничных: 180, -180, 0, пустое, текст) не приводит к падению.

**T-02. 🔴 Кнопка «Далее» не нажимается после заполнения всех полей (вкладка 3).**
Студент заполнил все поля, но не может перейти дальше — модуль непроходим.
- Диагноз (гипотеза): условие готовности шага (`все обязательные поля валидны → кнопка активна`) вычисляется неверно. Возможно, поле, помеченное обязательным, на деле опционально, либо валидатор не сбрасывает флаг ошибки после исправления.
- Требуется: найти, какое условие не выполняется при визуально заполненной форме; починить логику активации кнопки.
- Тест: заполнение всех полей вкладки 3 активирует «Далее».

### Уровень 2 — неверные расчёты (данные врут)

**T-03. 🔴 Длина трассы некорректно меняется при изменении стрел прогиба.**
Подтверждает опасение из ТЗ v2.0: формула длины дуги и/или проекция реализованы с ошибкой. Цифры длины реально неверны, а они уходят в экономику ПЗ-1.

Две станции не могут иметь одинаковое название. Blocking-валидация: при дубле — сообщение, дальше не пускать до исправления.

**T-09. Убрать надпись «MapLibre · OpenStreetMap» с экрана карты.**

## 5. ПЗ-1: Карта, трасса, кривые

### 5.1 Два независимых набора точек ✅ (не воспроизводить старый баг)

| Набор | Лимит | Семантика |
|---|---|---|
| **Станции** | 2 терминальные (А, Г) + до 2 промежуточных (Б, В) | Подписи, участвуют в корреспонденциях |
| **Вершины трассы** | без лимита | Геометрия хода: обход воды, гор, городов |

`routeLine`/`routeSegments` **не выводится из станций**. Два раздельных режима ввода на карте, по образцу Яндекс.Карт. Ранее реализованное автопостроение линии по станциям — баг, не воспроизводить.

### 5.2 🔄 Модель трассы: сегменты с кривизной

Принято в HANDOFF-2: ввод **радиуса** (не стрелы прогиба — см. T-11, требует финального подтверждения преподавателя).

```ts
// src/pz1/model/route.ts

export interface GeoPoint { lon: number; lat: number; }

export interface RouteVertex extends GeoPoint { id: string; }

/**
 * Сегмент между двумя соседними вершинами.
 * radiusKm === null  → прямой участок.
 * radiusKm > 0       → круговая кривая заданного радиуса.
 * Ограничение: R ≥ chord/2 (иначе дуга геометрически невозможна).
 */
export interface RouteSegment {
  id: string;
  fromVertexId: string;
  toVertexId: string;
  radiusKm: number | null;
  // вычисляемые (не хранить в JSON): chordKm, arcLengthKm, centralAngle
}

export interface RouteLine {
  vertices: RouteVertex[];
  segments: RouteSegment[];   // всегда vertices.length - 1
}
```

> [!warning] 🧩 ДОПУЩЕНИЕ — проверить по методичке
> Предполагается **дуга окружности постоянного радиуса**. Реальное проектирование ж/д использует **переходные кривые (клотоиды)** между прямой и круговой кривой. Методичка (стр. 7 ПЗ-1, «круговая кривая») говорит о круговых кривых — вероятно, клотоиды не требуются, но **подтвердить явно** перед финализацией. Если требуются — модель усложняется.

### 5.3 ✅ Расчёт длины — формулы и защита от краха

Обозначения на сегмент: `c` — хорда (км), `R` — радиус (км), `θ` — центральный угол, `L` — длина дуги.

**Центральный угол:**

$$\theta = 2 \arcsin\!\left(\frac{c}{2R}\right)$$

**Длина дуги:**

$$L = R \cdot \theta$$

**Прямой сегмент** (`radiusKm === null`): `L = c`.

**Обязательные защиты (прямо связано с T-01, T-03):**
1. `if (radiusKm === null) return chordKm;` — прямой участок, без тригонометрии.
2. `if (R < c/2) → ОШИБКА ВАЛИДАЦИИ`, не бросать исключение. `arcsin` от аргумента > 1 даёт `NaN` — источник краха. Проверять **до** вызова `arcsin`.
3. Аргумент `arcsin` зажимать в `[-1, 1]` на случай погрешности: `Math.asin(Math.min(1, Math.max(-1, c/(2*R))))`.
4. Любой некорректный числовой ввод → предсказуемая ошибка валидации, **не падение** (T-01).

**Контрольный тест (обязателен):** полуокружность `c=100, R=50` → `θ = 2·arcsin(100/100) = 2·arcsin(1) = π` → `L = 50·π ≈ 157.08`. Совпадает с половиной длины окружности радиуса 50. ✅

**Суммарная длина трассы:** `L_трассы = Σ L_i`. Показывать постоянно на экране, писать в JSON, включать в PDF.

**Поучастковое расстояние между станциями (T-05):** для каждой пары соседних станций — сумма длин сегментов трассы между ними. Показывать отдельно от суммарной длины.

### 5.4 ✅ Проекция — не считать в Web Mercator

Координаты в градусах, длины нужны в км. Прямой расчёт в Web Mercator завышает длину в ~1/cos(широты) раз — на широтах России (55–60°) это десятки процентов ошибки, которая молча уходит в экономику. **Это вероятная причина T-03.**

Требования:
1. Хорда — по **геодезической** (гаверсинус, R_Земли = 6371 км), не по декартовой разнице координат.
2. Дугу строить в **локальной касательной плоскости (ENU)**, центр — середина хорды, затем обратно в lon/lat для отрисовки.
3. Отрисовка дуги — полилиния ~64 точки на сегмент.

Всё в `src/pz1/geo/`, покрыть тестами. Контрольный пример длины хорды — реальная пара городов из вариантов, сверить с известным расстоянием.

### 5.5 ✅ Красная линия ВСМ поверх всех слоёв

- Линия трассы ВСМ — отдельным цветом (🧩 предложено `#E0182D`; если у школы есть утверждённый цвет линии ВСМ — использовать его).
- Слой линии добавляется **последним**, поверх базовой карты.
- Маркеры станций — **выше линии** (иначе линия перечеркнёт подписи).
- Порядок задавать через `beforeId` в `map.addLayer()` **явно**, не полагаться на порядок добавления (асинхронная загрузка стиля).

Порядок сверху вниз: подписи станций → маркеры → линия ВСМ → вершины трассы (в режиме правки) → базовая карта.

### 5.6 UI редактирования кривой

- Клик по сегменту → выделение + панель: поле «Радиус, км» (или стрела прогиба — по итогу T-11), справочный вывод второй величины.

- 🧩 Post-MVP: перетаскивание середины сегмента мышью. Только **после** работающего числового ввода.
- ❓ **Нормативный минимум радиуса** (в проектировании ВСМ зависит от расчётной скорости; методичка упоминает 10000 м / 400 км/ч). Если норматив в методичке задан — warning-валидация при R ниже нормы. **Число брать из методички.**

## 6. ПЗ-1: Таблицы корреспонденций

### 6.1 🔄 Количество таблиц динамическое ✅

Не 4 фиксированные. Одна таблица на каждую **корреспонденцию** (пару станций).

$$N_{\text{таблиц}} = C(n,2) = \frac{n(n-1)}{2}$$

| Станций | Пары | Таблиц |
|---|---|---|
| 2 (А, Г) | А-Г | 1 |
| 3 (А, Б, Г) | А-Б, А-Г, Б-Г | 3 |
| 4 (А, Б, В, Г) | А-Б, А-В, А-Г, Б-В, Б-Г, В-Г | 6 |

**Число шагов ПЗ-1 переменное:** `3 + 2×C(n,2)` (из HANDOFF-2), от 5 до 15.

Требования:
1. Набор таблиц пересобирается при изменении числа станций, введённые данные по сохранившимся парам **не теряются**.
2. Порядок пар — лексикографически (А-Б, А-В, А-Г, Б-В, Б-Г, В-Г).
3. 🧩 Пара ненаправленная (А-Б = Б-А, одна таблица). Пример преподавателя это подтверждает. Если методичка требует направлений — таблиц вдвое больше, **проверить**.

### 6.2 ✅ 6 видов транспорта — подтверждено методичкой

## 7. ПЗ-1: Таблица коэффициента дискомфорта 🔄 (пересмотр)

**Обратная связь преподавателя:** «Коэффициент дискомфорта заполняется 1 раз в соответствии с табл.» + приложена таблица + «см. pdf к ПЗ-1».

**Что это меняет по сравнению с ТЗ v2.0.** Раньше «индекс дискомфорта» был выходным показателем (0=зелёный, 1=красный). По факту это **входная таблица-матрица**, которую студент заполняет один раз: строки — критерии комфорта, столбцы — 6 видов транспорта, значения 0…1. Это **входной параметр модели** (аналог 18 весов), а не результат.

### 7.1 Структура таблицы ✅ (сверено с методичкой, стр. 22)

**Столбцы:** те же 6 видов транспорта (§6.2), в том же порядке.

**Строки — 9 критериев (дословно из методички):**
1. Индекс плотности пассажиров в салоне
2. Индекс уровня шума, вибрация, плавности хода, пересадки
3. Индекс качества работы климат-контроля, наличие неприятных запахов и пр.
4. Индекс объёма и качества дополнительных услуг, оказываемых пассажиру
5. Индекс технической безопасности транспортного средства (индекс аварийности), предсказуемость в пути
6. Индекс личной безопасности (охрана, безопасность, вероятность кражи)
7. Наличие свободных мест
8. Сложность приобретения билета
9. Коэффициент эластичности к уровню комфорта

**Значения:** вводит студент, диапазон **0…1** (0 = комфортно, 1 = дискомфортно). Дословно из примечания методички: «значения могут находиться в диапазоне от 0 до 1, где 0 – комфортно, 1 – дискомфортно».

> [!note] Важно
> В самой методичке таблица **пустая** — значения не заданы, их проставляет студент. Значит, это НЕ константы, а поля ввода. Заполняется один раз на модуль (не по корреспонденциям).

### 7.2 Требования к реализации ✅
1. Матрица 9×6, ячейки — числовой ввод 0…1.
2. Валидация: значение вне [0,1] — blocking-ошибка (§9.5).
3. 🔄 **Цветовая индикация ячейки** — уточнение прежнего «0 зелёный / 1 красный»: раз значение непрерывное в [0,1], красить **градиентом** зелёный→красный по значению. Цвет — вспомогательный, **рядом обязательно само число** (дальтонизм, ч/б печать).
4. Столбец ВСМ — присутствует и заполняется (это одна из сравниваемых альтернатив), но как столбец таблицы дискомфорта **неудаляем**, как и везде.
5. Заполняется 1 раз, результат идёт в модель прогноза как вход.

## 8. Персистентность — только JSON-файл ✅ (блокер снят)

**Решение команды:** прогресс сохраняется в JSON-файл и загружается из него. **Ни localStorage, ни сервера, ни Google Forms, ни загрузки по ID.** Сохраняет принцип «бэкенда нет».

### 8.1 Две роли одного файла 🔄

Файл теперь несёт две разные функции — не смешивать:

```
{
  schemaVersion: "1.1",              // ← поднята: схема изменилась
  passport: { team, lineTitle, defaultVariant?, createdAt },
  completed: { pz1?: {...}, ... },   // финализированные результаты (межмодульный мост)
  progress?: {                        // ← НОВОЕ: незавершённый прогресс внутри модуля
    pz1?: {
      currentStepId: string,          // на каком шаге сохранились
      draft: { ... }                  // черновые значения по всем начатым шагам
    }
  }
}
```

- `completed.pzN` — готовая работа, идёт в следующий ПЗ. Не трогать черновиками.
- `progress.pzN` — «пауза», продолжить с этого места. Может содержать неготовые значения.

### 8.2 Требования ✅
1. **Кнопка «Сохранить» на каждом шаге**, срабатывает в любой момент — пишет весь JSON, включая незавершённый текущий шаг.
2. **Восстановление места:** при загрузке файла открывается тот шаг (`currentStepId`), на котором сохранились, а не старт модуля.
3. **Восстановление данных:** поля этого и всех пройденных шагов заполнены сохранёнными значениями.
4. **Каждый ПЗ обязан работать с чистого листа** — загрузка файла удобство, не обязательный вход.
5. Обратная связь на сохранение: «Сохранено, 14:32» рядом с кнопкой.

### 8.3 Абстракция ✅
Слой хранения — за интерфейсом, компоненты не знают деталей:

```ts
export interface DraftStorage {
  loadFromFile(file: File): Promise<VsmBridge>;
  saveToFile(bridge: VsmBridge): void;         // скачивание Blob
  restorePosition(bridge: VsmBridge, pz: PzId): { stepId: string; draft: PzDraft } | null;
}
```
Реализация одна конкретная — `JsonFileDraftStorage`. Ни один компонент не трогает файловую систему напрямую.

### 8.4 ⚠️ Непроверенные риски (открыть в open-questions)
1. **Скачивание файла из iframe iSpring.** `<a download>` внутри Web Object может блокироваться sandbox-атрибутами iframe. **Проверить на живом плеере до финализации** — иначе весь механизм упрётся в песочницу. Тот же класс риска, что postMessage.
2. **Загрузка через `<input type=file>` в iframe** — аналогично проверить.
3. **UX множественных скачиваний:** каждое «Сохранить» роняет новый файл в «Загрузки» (`...(1).json, (2).json`). Продумать имя файла и инструкцию студенту грузить свежий.
4. ❓ **Один файл на всю работу студента (все 8 ПЗ) или свой на каждый ПЗ?** По логике межмодульного моста — один общий, накопительный. **Подтвердить.**

> Прямо связано с диагностикой Кодекса: `annualFlow` сейчас — **ручное поле**. После реализации прогноза должно стать **вычисляемым**, иначе нарушает «живой итог».

### 9.4 🧩 Уникальность имён станций
Blocking-валидация (T-04): дубль названия — ошибка, дальше не пускать.

### 9.5 ✅ Валидация ввода — три уровня

| Уровень | Поведение | Пример |
|---|---|---|
| **Формат** | Не даёт ввести | буквы в числовом поле |
| **Blocking** | Ошибка, не пускает дальше | отрицательная длина, пустое обязательное, дубль имени станции, значение дискомфорта вне [0,1] |
| **Warning** | Предупреждает, пройти можно | радиус ниже норматива, нетипичное значение |

- Разделение blocking/warning для ПЗ-1 — в `pz1-copy-and-validation.md`, следовать ему.
- Тон человечный: не «Ошибка валидации», а «Длина не может быть отрицательной — проверьте значение».
- Сообщение рядом с полем, не общим списком.
- Не ругаться, пока поле в фокусе и студент печатает — проверка по `blur`.

### 9.6 ✅ Русская типографика — неразрывные пробелы
Короткие слова (1–2 буквы: предлоги, союзы) не остаются в конце строки — `\u00A0` к следующему слову.

```ts
export function nbsp(text: string): string {
  return text.replace(/(^|\s)([а-яёa-z]{1,2})\s+/gi, '$1$2\u00A0');
}
```
Применять ко всем видимым русским текстам интерфейса **и в PDF**. Не применять к пользовательскому вводу, числам, коду.
🧩 Рекомендуется также: неразрыв между числом и единицей (`250 км`), тире `—` с неразрывным пробелом перед ним. Подтвердить.

## 11. Организационное — требует решения, не кода

### 11.1 ❓ LTI — изучить, потом решать

Преподаватель просит «почитать про LTI». Это **не мелочь** — потенциально смена интеграционной архитектуры.

**Что такое.** LTI (Learning Tools Interoperability) — стандарт встраивания внешних инструментов в LMS (Moodle, Canvas, и т.п.). Альтернатива/дополнение к встраиванию как Web Object в iSpring через iframe.

**Что даёт (и что задевает):**
- Identity студента из LMS (кто вошёл) — то, чего проект сознательно лишился.
- Возврат оценки в журнал LMS (Assignment and Grade Services).
- Обычно требует **серверную часть** (LTI-провайдер) — прямой конфликт с «бэкенда нет».

**Риск для только что принятых решений.** Если вуз хочет LTI — отвергнутая «загрузка по ID» и хранение прогресса могут вернуться уже как требование стандарта, а не прихоть. Плюс LTI 1.3 — это OAuth2/OIDC, подписи, регистрация tool. Не «внедрить за вечер».

**Что делать сейчас (рекомендация):** НЕ бросаться внедрять. Сначала выяснить у преподавателя: LTI — пожелание «на будущее» или требование вуза к финальной поставке? От ответа зависит, трогает ли это архитектуру сейчас.
- Могу подготовить отдельную справку «LTI: что даёт проекту, чем противоречит текущей архитектуре, объём работ» для предметного разговора с преподавателем.

### 11.2 ⚠️ КСГ — влияет на сроки

Преподаватель: «сразу после последних правок по ПЗ-1 переходим к КСГ… где посмотреть текущее состояние?»

4. **Каждая расчётная функция — с тестом** на примере из методички/фикстуры.
5. **Нет данных — сказать.** Не подставлять правдоподобные числа.

7. **Документы — в репозитории**, не текстом в чат (иначе `-2`-дубли и битые ссылки).
