## 1. Что не меняется (база из HANDOFF, действует)

Перечислено, чтобы исполнитель не «переоткрывал» решённое.

### 1.1 Технологии ✅ ПОДТВЕРЖДЕНО
- React 19 + TypeScript + Vite, тесты — Vitest
- Стилизация — обычный CSS с кастомными свойствами (`styles.css`). Tailwind и Framer Motion **не подключены**; подключение — отдельное явное решение, не самовольно
- **Бэкенда нет.** Ни Django, ни Postgres, ни docker-compose под сервисы приложения
- Деплой — статическая сборка `vite build` за одним Caddy/Nginx
- К подключению: `maplibre-gl`, `katex`, `@react-pdf/renderer`

### 1.2 Упаковка и роутинг ✅ ПОДТВЕРЖДЕНО
8 отдельных Web Object в iSpring, **один билд**, роутинг `?pz=N`. Не единый Web Object с внутренним меню.

### 1.3 Ограничения iframe ✅ ПОДТВЕРЖДЕНО
Нет логина/регистрации, глобальных футеров, тяжёлых хедеров. `h-screen` + `overflow-hidden` на корне, внутренние области скроллятся изолированно, двойного скролла быть не должно.

### 1.4 Жизненный цикл модуля ✅ ПОДТВЕРЖДЕНО (с уточнением в §7.4)
Интро → теория (оверлей, не отдельный маршрут) → задание (массив шагов) → итог. Строго линейно вперёд: **перескок через непройденный шаг запрещён**. Единственный навигационный элемент — прогресс-трасса, дублирующего сайдбар-меню нет. Сырой JSON студенту на экране не показывается никогда.

### 1.5 Модель работ ✅ ПОДТВЕРЖДЕНО
Работы **персональные**. Команда 5–6 человек существует организационно, но сдаёт каждый сам. Преподаватель проверяет вручную по PDF. JSON-мост — «пред-заполняет, никогда не блокирует»: **каждый ПЗ обязан работать с чистого листа**.

### 1.6 PDF-отчёт ✅ ПОДТВЕРЖДЕНО
Клиентская генерация через `@react-pdf/renderer` (собственный движок, не print-to-PDF браузера). Академический печатный стиль: serif (Times), чёрные рамки таблиц, минимум цвета, колонтитул, нумерация страниц, карта как PNG с подписью «Рисунок N». `design-reference.html` в PDF **не применяется** — у печати своя дизайн-система.

### 1.7 Таксономия шагов ✅ ПОДТВЕРЖДЕНО
13 `kind`, все прототипированы в `design-reference.html`. Изменений нет. Два блока (`drag-drop-scheme` для ПЗ5, `schedule-graph` для ПЗ7) остаются черновиком **только стиля** — механика не утверждена.

### 1.8 Варианты заданий ✅ ПОДТВЕРЖДЕНО
Преподаватель называет номер варианта очно. `defaultVariant?: number` в паспорте, `variants.ts` со статическими пресетами в модулях, где методичка задаёт вариантный набор. Селектор подставляет **исходные данные, не решение**. Наличие вариантов — не универсально, сверять по методичке каждого ПЗ.

### 1.9 Граф зависимостей ✅ ПОДТВЕРЖДЕНО (без изменений)

## 2. Блокеры — работы не начинать до ответа

### ⛔ БЛОКЕР-1. Цветовая палитра: какая из двух действует

**Суть конфликта.** Ранее было принято решение: цвета сэмплируются **из PDF методичек**, официальный брендбук РУТ МИИТ (`#1B365D` / `#0072CE`) сознательно **не используется**. Зафиксировано: indigo `#3a288b` + teal `#08a696`.

Теперь передан `SCHOOLVSMCOLOURS.svg` с иным основным цветом. Это **не уточнение оттенка, а отмена прежнего принципа выбора цвета**.

**Что в SVG (извлечено из `fill` атрибутов, 5 свотчей):**

| # | HEX | Позиция в файле | Подпись в свотче |
|---|---|---|---|
| 1 | `#003D84` | x=40 | 003D84 |
| 2 | `#08A696` | x=240 | 08A696 |
| 3 | `#B9D2FF` | x=440 | B9D2FF |
| 4 | `#F3F7FF` | x=640 (фон-подложка) | F3F7FF |
| 5 | `#232323` | x=840 | 232323 |

**Сопоставление со старой палитрой:**

| Роль | Было | Стало | Комментарий |
|---|---|---|---|
| Основной | `#3a288b` (indigo) | `#003D84` (тёмно-синий) | **Конфликт.** Разные цвета, не оттенки одного |
| Акцент | `#08a696` (teal) | `#08A696` | **Совпадает буквально.** Регистр не важен |
| Светлый тон | не было | `#B9D2FF` | Новая роль |
| Фон | не было (белый) | `#F3F7FF` | Новая роль |
| Тёмный нейтральный | не было | `#232323` | Новая роль |

**Требуется ответ на 3 вопроса:**
1. `#003D84` **полностью заменяет** `#3a288b`, или это цвет для отдельного контекста (например, только шапка/обложка), а индиго остаётся в интерфейсе?
2. Палитра — обязательная для **всех 8 ПЗ** или только для новых экранов?
3. Отменяется ли сам принцип «цвет из методичек» — то есть при будущих расхождениях приоритет теперь у брендовой палитры школы, а не у PDF?

**Почему это блокер, а не «просто поправить переменные».** `design-reference.html` — единственный источник дизайна, из него исполнители копируют буквально. Если переписать переменные, не отменив прежнее правило, получим два противоречащих источника истины и повтор ситуации из §12. Пересборка референса — 24 блока, работа не пятиминутная, делать её дважды не нужно.

**Пока не отвечено:** новые экраны верстать на CSS-переменных (`--color-primary` и т.д.), **не хардкодить hex в компонентах**. Тогда смена палитры = правка одного файла.

### ⛔ БЛОКЕР-2. Персистентность прогресса: три несовместимых предложения

**Суть.** В записках со встречи зафиксированы три разных подхода от разных людей, между собой не согласованных:

| # | Предложение (как прозвучало) | Что означает технически |
|---|---|---|
| A | «Если студент работает на своём ПК — то localStorage» | Автосохранение в браузере. Привязка к устройству+браузеру |
| B | «Забить про гугл формы и всё же брать JSON» | Явный экспорт/импорт файла. Носитель — сам студент |
| C | «Мб по айдишнику подгружать чуваков, подумать над количеством на хранение» | Загрузка сохранённой работы по идентификатору |

**Почему это блокер.** Вариант C в буквальном прочтении **требует серверного хранилища** — то есть отменяет решение «бэкенда нет», которое лежит в основании всей архитектуры (§1.1) и деплоя. Это не деталь UX, это разворот фундамента. Реализовать «наполовину» нельзя.

**Разбор вариантов — для принятия решения, не как рекомендация:**

**A. localStorage**
- ✅ Ноль инфраструктуры, работает офлайн, прогресс не теряется при случайном закрытии вкладки
- ❌ Привязано к браузеру и устройству. Учебный класс с общими ПК = чужой прогресс в твоём браузере. Инкогнито/очистка кэша = всё пропало
- ❌ **Отдельный риск: iframe.** Web Object внутри iSpring — сторонний контекст. Браузеры (Safari ITP, режимы блокировки сторонних данных) могут ограничивать storage в iframe. **Не проверено на реальном iSpring-плеере** — см. ❓ВОПРОС-3
- Оценка: низкая сложность, ~1–2 дня

**B. Экспорт/импорт JSON**
- ✅ Уже спроектировано и утверждено (§1.5), работает всюду, кросс-девайсно, соответствует «бэкенда нет»
- ✅ Студент физически владеет своей работой
- ❌ Ручное действие; студент может забыть скачать и потерять всё
- Оценка: уже в плане, дополнительной сложности нет

**C. Загрузка по ID**
- ✅ Самый удобный сценарий для студента
- ❌ **Нужен сервер + хранилище + вопросы персональных данных.** Отменяет §1.1
- ❌ «Подумать над количеством на хранение» — прямое следствие: появляется квота, ретеншн, чистка. Это уже эксплуатируемый сервис, а не статика
- 🧩 Есть промежуточная трактовка: «ID» = локальный список профилей **в том же браузере** (несколько студентов на одном ПК, каждый под своим именем). Это по сути вариант A с профилями, без сервера. **Является ли это тем, что имелось в виду — неизвестно, требует уточнения у автора реплики**
- Оценка: с сервером — недели + новая инфраструктура; как профили поверх A — +1 день

**Рекомендуемая формулировка вопроса команде:** не «localStorage или JSON» (они не взаимоисключающие — B уже утверждён, A — надстройка над ним), а: **«готовы ли мы заводить сервер ради варианта C, или C — это профили в localStorage?»**

**Что можно делать, не дожидаясь ответа.** Слой хранения обязан быть абстрагирован интерфейсом — тогда выбор реализации не влияет на остальной код:

```ts
// src/shared/persistence/types.ts
export interface DraftStorage {
  load(pz: PzId): Promise<PzDraft | null>;
  save(pz: PzId, draft: PzDraft): Promise<void>;
  clear(pz: PzId): Promise<void>;
  /** Доступно ли хранилище в текущем окружении (iframe/приватный режим). */
  isAvailable(): boolean;
}
```

Реализации `LocalStorageDraftStorage` / `NoopDraftStorage` подставляются в одном месте. Никакой компонент не обращается к `window.localStorage` напрямую. Это требование ✅ **ПОДТВЕРЖДЕНО** независимо от исхода спора.

## 4. ПЗ1 — Карта: кривые, радиусы, длина трассы

### 4.1 Что остаётся из прежнего решения ✅ ПОДТВЕРЖДЕНО

Напоминание, потому что это уже один раз реализовали неверно.

**Два независимых набора точек, один не выводится из другого:**

| Набор | Лимит | Семантика |
|---|---|---|
| **Станции** | ровно 2 терминальные (А, Г) + до 2 промежуточных (Б, В) | Имеют подписи, участвуют в расчётах корреспонденций |
| **Вершины линии трассы** (`routeLine`) | **без лимита** | Геометрия хода трассы: обход воды, гор, населённых пунктов |

**Ранее обнаруженный баг (не воспроизводить):** линия трассы строилась автоматически как ломаная по станциям. Это неверно. `routeLine` **не является производной от `stations`**. Два раздельных режима ввода на карте — «Станция» / «Линия трассы», по образцу инструментов Яндекс.Карт.

Третий инструмент (полигоны регионов) — ❓ **ОТКРЫТО**, в MVP не входит.

### 4.2 🔄 ИЗМЕНЕНО: линия трассы становится последовательностью сегментов

**Требование со встречи:** *«Добавить радиус между точками (насколько км натянули дугу относительно двух точек)»*, *«параметры кривых нужно, делим по важным точкам кривые/прямые между точками»*, *«чтобы было не чисто прямые линии»*.

**Что меняется в модели данных.** Было — массив точек. Стало — массив точек **плюс** параметр кривизны на каждом промежутке между соседними точками.

```ts
// src/pz1/model/route.ts

export interface GeoPoint {
  lon: number;
  lat: number;
}

/** Вершина линии трассы. Порядок в массиве = порядок вдоль трассы. */
export interface RouteVertex extends GeoPoint {
  id: string;
}

/**
 * Промежуток между двумя соседними вершинами.
 * sagitta = «на сколько км натянули дугу относительно прямой»
 * (стрела прогиба — расстояние от середины хорды до середины дуги).
 * sagitta === 0  → прямой участок.
 * Знак задаёт сторону выпуклости: + влево по ходу, − вправо.
 */
export interface RouteSegment {
  id: string;
  fromVertexId: string;
  toVertexId: string;
  sagittaKm: number;      // ввод студента
  // Ниже — вычисляемые, не хранить в JSON-мосте, пересчитывать:
  // chordKm, radiusKm, arcLengthKm
}

export interface RouteLine {
  vertices: RouteVertex[];
  segments: RouteSegment[];   // всегда vertices.length - 1 штук
}
```

**Почему параметр ввода — стрела прогиба, а не радиус.** Формулировка в записках — «насколько км натянули дугу относительно двух точек» — это буквально стрела прогиба, а не радиус. Для студента это интуитивнее: он «оттягивает» линию мышью и видит, на сколько километров отошёл от прямой. Радиус при этом **вычисляется и показывается рядом**, потому что радиус — величина, которой оперирует методичка (нормы на радиусы кривых ВСМ).

⚠️ 🧩 **ДОПУЩЕНИЕ, требует проверки по методичке ПЗ1:** предполагается, что кривая — **дуга окружности постоянного радиуса**. В реальном проектировании железных дорог между прямой и круговой кривой ставится **переходная кривая** (клотоида), и методичка может этого требовать. Если требует — модель усложняется (появляется длина переходной кривой), и это надо заложить сразу, а не переделывать. **Проверить раздел методички про план трассы до начала реализации.**

### 4.3 ✅ Расчёт длины — формулы

Пусть для сегмента:
- `c` — длина хорды (расстояние по прямой между вершинами), км
- `h` — стрела прогиба `sagittaKm`, км
- `R` — радиус кривой, км
- `L` — длина дуги, км

**Радиус по хорде и стреле:**

$$R = \frac{h}{2} + \frac{c^2}{8h}$$

**Центральный угол:**

$$\theta = 2 \arcsin\!\left(\frac{c}{2R}\right)$$

**Длина дуги:**

$$L = R \cdot \theta$$

**Граничный случай:** при `h = 0` формулы вырождаются (деление на ноль). В коде — явная ветка: `if (Math.abs(h) < EPS) return chordKm;`

**Проверка формул (обязательный юнит-тест).** Полуокружность: `c = 100`, `h = 50`.
- `R = 50/2 + 100²/(8·50) = 25 + 25 = 50` км
- `θ = 2·arcsin(100/100) = 2·(π/2) = π`
- `L = 50 · π ≈ 157.08` км — совпадает с половиной длины окружности радиуса 50. ✅

**Суммарная длина трассы:**

$$L_{\text{трассы}} = \sum_{i} L_i$$

🔄 **ИЗМЕНЕНО — новое требование:** *«Нужна длина всей трассы полученной»*. Суммарная длина отображается **постоянно на экране карты** (не только в итогах) и попадает в JSON-мост и в PDF.

### 4.4 🧩 Проекция — архитектурное решение, зафиксировать явно

Координаты вводятся в градусах (`lon`/`lat`), а считать длины и строить дуги нужно в метрах. Прямой расчёт в Web Mercator даст **систематически завышенную длину**: масштабный коэффициент Меркатора растёт как 1/cos(широты), и на широтах России (55–60°) ошибка составит десятки процентов. Это ошибка, которую легко не заметить, а результат уйдёт в экономические расчёты ПЗ1.

**Требование:**
1. Длину хорды считать **по геодезической** (гаверсинус по сфере радиуса 6371 км) — не по декартовой разнице координат
2. Дугу строить в **локальной касательной плоскости** (ENU), начало — середина хорды сегмента, затем обратное преобразование в `lon/lat` для отрисовки
3. Отрисовывать дугу полилинией из ~64 промежуточных точек на сегмент (достаточно гладко, не перегружает MapLibre)

Функции вынести в `src/pz1/geo/` и покрыть тестами. Контрольный пример для теста длины — взять реальную пару городов из вариантов задания и сверить с известным расстоянием.

### 4.5 🔄 ИЗМЕНЕНО: красная линия ВСМ поверх всех слоёв

**Требование:** *«ВСМ другим цветом и в конце поставить»*, *«Красная линия должна быть»*.

- Линия трассы ВСМ рисуется цветом `--color-route-hsr` (🧩 предложено `#E0182D`; если у школы есть утверждённый цвет для линии ВСМ — использовать его, см. ⛔БЛОКЕР-1, вопрос 2)
- Слой линии добавляется **последним**, поверх всех слоёв базовой карты и поверх полигонов/подложек
- Маркеры станций — **выше линии** (иначе линия перечеркнёт подписи)

Порядок слоёв сверху вниз: подписи станций → маркеры станций → линия ВСМ → вершины `routeLine` (в режиме редактирования) → базовая карта.

В MapLibre порядок задаётся порядком добавления либо параметром `beforeId` в `map.addLayer()`. **Не полагаться на порядок добавления неявно** — указывать `beforeId` явно, иначе при асинхронной загрузке стиля слои встанут произвольно.

- Клик по сегменту → сегмент выделяется, появляется панель с полем «Стрела прогиба, км» и справочным «Радиус: N км»
- 🧩 Опционально (post-MVP): перетаскивание середины сегмента мышью, `sagittaKm` считается из позиции курсора. Реализовывать **после** работающего числового ввода, не вместо
- Валидация — см. §7.3

## 5. ПЗ1 — Таблицы корреспонденций

### 5.1 🔄 ИЗМЕНЕНО: количество таблиц динамическое

**Было (HANDOFF §9):** «4 таблицы потребительских свойств» — фиксированный набор.

**Стало.** Из записок: *«таблица для каждой пары А-Б, А-В, А-Г, Б-В, Б-Г, В-Г»*, *«Таблица делается для каждой корреспонденции»*, *«Таблиц должно быть много для каждой корреспонденции!»*.

Количество таблиц = число сочетаний из числа станций по 2:

$$N_{\text{таблиц}} = C(n, 2) = \frac{n(n-1)}{2}$$

| Станций на карте | Пары | Таблиц |
|---|---|---|
| 2 (только А и Г) | А-Г | **1** |
| 3 (А, Б, Г) | А-Б, А-Г, Б-Г | **3** |
| 4 (А, Б, В, Г) | А-Б, А-В, А-Г, Б-В, Б-Г, В-Г | **6** |

Пример из записок (6 таблиц) соответствует случаю 4 станций. **Прежняя цифра «4 таблицы» недействительна.**

**Следствия, которые нужно реализовать:**
1. Набор таблиц **пересобирается** при добавлении/удалении станции на карте. Уже введённые данные по сохранившимся парам — **не терять**
2. Порядок пар — вдоль трассы, лексикографически по индексам станций (А-Б, А-В, А-Г, Б-В, Б-Г, В-Г), как в примере
3. Направление корреспонденции: 🧩 **ДОПУЩЕНИЕ** — пара считается ненаправленной (А-Б и Б-А это одна таблица). Пример из записок содержит только по одной комбинации на пару, что это подтверждает. Если методичка требует раздельного учёта по направлениям — таблиц будет вдвое больше, **проверить**

```ts
// src/pz1/model/correspondence.ts

export type StationId = string;

export interface CorrespondencePair {
  /** Стабильный ключ, например "A-B". Не пересоздавать при перерисовке. */
  key: string;
  fromStationId: StationId;
  toStationId: StationId;
}

export interface CorrespondenceTable {
  pairKey: string;
  /** Столбцы = виды транспорта. Порядок фиксирован, состав редактируем. */
  activeModes: TransportModeId[];
  /** Значения: [modeId][rowId] -> число. */
  values: Record<TransportModeId, Record<string, number | null>>;
}
```

### 5.2 🔄 ИЗМЕНЕНО: удаление столбцов (видов транспорта)

**Требование:** *«Необходимо внедрить возможность удаления столбца в таблицах»*, *«сделать исключение между точками если такого вида транспорта нет»*.

Смысл — предметный, а не UI-удобство: **между конкретной парой городов какого-то вида транспорта физически не существует** (например, нет прямого сообщения, нет водного пути). Такой вид надо исключить именно для этой пары, а не глобально.

**Требования:**
1. Удаление столбца действует **в пределах одной таблицы** (одной корреспонденции). В других парах этот же вид транспорта остаётся
2. Действие обратимо: рядом с таблицей — список исключённых видов с возможностью вернуть
3. Состав `activeModes` сохраняется в JSON-мосте вместе со значениями
4. Полный перечень видов транспорта берётся из `docs/examples/pz1-passenger-flow.md` — **не составлять список самостоятельно**

### 5.3 ⛔ БЛОКЕР-3: как исключение вида транспорта влияет на расчёт

Модель прогноза пассажиропотока в ПЗ1 — модальный сплит логит-типа: доля каждого вида транспорта считается через отношение его «полезности» к сумме по всем видам. Если вид удалён из таблицы — **что происходит со знаменателем?**

Два принципиально разных поведения:
- **(а) Перераспределение.** Вид исключается из суммы, его доля пропорционально расходится по оставшимся. Сумма долей остаётся 100%
- **(б) Нулевая полезность.** Вид остаётся в формуле с нулевой долей; результат численно близок к (а), но не идентичен

Разница влияет на итоговые цифры пассажиропотока, а значит — на экономику всего ПЗ1.

**Требуется:** сверить с Excel-моделью, разобранной в `docs/examples/pz1-passenger-flow.md`, и если там этот случай не покрыт — **задать вопрос преподавателю**. Не выбирать самостоятельно.

До ответа: реализовать таблицы и удаление столбцов (UI + модель данных), расчётную функцию оставить за интерфейсом с явным `// ⛔ БЛОКЕР-3` в месте, где решается судьба знаменателя.

### 6.1 ✅ Кнопка сохранения на каждом шаге

**Требование:** *«Добавить кнопку сохранения для каждого этапа»*, *«Кнопка перезаписи json на каждом участке»*.

- Кнопка «Сохранить» присутствует на **каждом** шаге задания, не только в конце
- Действие: записать текущее состояние шага в накопительный JSON-мост (перезаписать секцию этого шага)
- **Куда именно пишется** — определяется реализацией `DraftStorage` (см. ⛔БЛОКЕР-2). Компонент кнопки об этом не знает
- Обратная связь обязательна: короткий статус «Сохранено, 14:32» рядом с кнопкой. Без него студент не понимает, сработало ли
- ⚠️ Кнопка **не должна** быть единственным способом не потерять данные: переход между шагами тоже сохраняет состояние. Кнопка — для явного контроля, а не костыль

### 6.2 ✅ Подсказки «i» у показателей

**Требование:** *«i для показателей чтоб объяснить кто что значит»*.

- Иконка «i» рядом с каждым из 13 итоговых показателей ПЗ1
- По наведению/тапу — тултип: что означает показатель, в чём измеряется, как интерпретировать значение
- Мобильный/тач: тултип по тапу, закрывается по тапу вне области. Только `:hover` — недостаточно
- Доступность: `aria-describedby`, фокусируемый триггер
- **Тексты подсказок берутся из методички.** Если формулировки в методичке нет — вопрос преподавателю. Не сочинять определения инженерных показателей
- Компонент — общий (`shared/ui/InfoTooltip`), применим и в других ПЗ

### 6.3 🔄 Индекс дискомфорта — цветовая индикация

**Требование:** *«Индекс дискомфорта — 0 зелёным, 1 красным, чтобы не путаться»*.

- Значение 0 → `--color-success`, значение 1 → `--color-danger`
- ❓ **ОТКРЫТО:** индекс **бинарный (только 0 или 1)** или **непрерывный в диапазоне 0…1**?
  - Если бинарный — два состояния, две краски
  - Если непрерывный — нужна градиентная шкала между зелёным и красным, и надо решить, что в середине
  - **Уточнить по методичке.** До уточнения реализовать бинарно (буквально по формулировке), логику вынести в отдельную функцию, чтобы замена на шкалу была точечной
- ⚠️ Цвет — **не единственный** носитель смысла: рядом с цветом обязательно числовое значение и словесная метка. Иначе показатель нечитаем при дальтонизме и в ч/б печати PDF

### 6.4 ✅ «Живой» итоговый экран

**Требование:** *«Важно предусмотреть, чтоб конечный итог был "живым", можно назад отойти чтоб что-то поменять и посмотреть заново результаты»*.

**Это уточнение §1.4, а не отмена.** Правило «нельзя перескочить **вперёд** через непройденный шаг» остаётся. Движение **назад** по уже пройденным шагам — разрешено и было разрешено.

Что требуется дополнительно:
1. С экрана «Итог» можно вернуться на **любой** пройденный шаг
2. После правки — вернуться на «Итог», где **все зависимые величины пересчитаны**
3. Пересчёт **автоматический**, без кнопки «пересчитать». Производные значения не хранятся как «замороженные» копии, а выводятся из исходных данных
4. Прогресс-трасса при возврате назад **не сбрасывает** пройденные шаги

**Архитектурное следствие ✅ ПОДТВЕРЖДЕНО:** в состоянии модуля хранятся **только вводимые студентом данные**. Все производные (длина трассы, доли модального сплита, 13 показателей) — вычисляемые селекторы поверх состояния. Кэшировать можно, но кэш должен инвалидироваться от входов. Хранение рассчитанных значений в состоянии наравне с вводом — источник рассинхрона, запрещено.

### 6.5 ✅ Валидация ввода

**Требование:** *«Сделать проверку значений на валидность значений»*.

Три уровня, различать явно:

| Уровень | Поведение | Пример |
|---|---|---|
| **Формат** | Не даёт ввести | буквы в числовом поле, больше N знаков после запятой |
| **Blocking** | Ошибка, дальше не пускает | отрицательная длина, пустое обязательное поле, доли не в сумме 100% |
| **Warning-only** | Предупреждение, пройти можно | нетипично большое/малое значение, радиус ниже рекомендуемого |

- Разделение blocking / warning-only для ПЗ1 уже описано в `docs/pz1-copy-and-validation.md` — **следовать ему**, новые правила туда же дописывать
- Тон сообщений — по §1.4: человечный, объясняющий, без канцелярита. Не «Ошибка валидации поля», а «Длина не может быть отрицательной — проверьте значение»
- Сообщение — **рядом с полем**, не общим списком наверху
- ⚠️ Валидация не должна мешать промежуточному состоянию ввода: пока поле в фокусе и студент печатает — не ругаться. Проверка по `blur` или с задержкой

### 6.6 ✅ Русская типографика — неразрывные пробелы

**Требование (упомянуто дважды):** *«Признак хорошего тона — перенесение двубуквенных и однобуквенных слов на новую строчку»*.

Правило: короткие слова (предлоги, союзы, частицы из 1–2 букв) не должны оставаться в конце строки — они переносятся на следующую строку вместе со словом, к которому относятся. Реализуется неразрывным пробелом `\u00A0` (`&nbsp;`).

```ts
// src/shared/text/typography.ts

/**
 * Приклеивает короткие слова (1–2 буквы) к следующему слову
 * неразрывным пробелом. Применять ко всем видимым русским текстам.
 */
export function nbsp(text: string): string {
  return text.replace(/(^|\s)([а-яёa-z]{1,2})\s+/gi, '$1$2\u00A0');
}
```

**Где применять:**
- Все тексты интерфейса: заголовки, подписи, подсказки, сообщения валидации, тексты теории
- **Тексты в PDF-отчёте** — там перенос особенно заметен
- Не применять к: пользовательскому вводу (названия станций студента), числам, коду

**Дополнительно рекомендуется** (того же класса правила, ⚠️ не звучало на встрече — предлагается, требует «да/нет»):
- Неразрывный пробел между числом и единицей измерения: `250 км`, `18 шт.`
- Неразрывный пробел после инициалов и в сокращениях: `т. е.`, `им. Ленина`
- Тире — длинное `—` с неразрывным пробелом **перед** ним

Централизовать в одной утилите, применять на уровне общего текстового компонента, а не вручную в каждой строке.

## 10. Требования к исполнителям

Повтор действующих правил — они нарушались.

1. **Дизайн копируется из `design-reference.html` буквально.** Не реконструировать по описанию. Если нужного блока в референсе нет — **спросить**, а не досочинить по аналогии
2. **Не переписывать файлы целиком** без явной команды — точечные правки
3. **Перед объёмной новой логикой — сначала план** (файлы, интерфейсы), потом код
4. **Каждая расчётная функция — с тестом** на примере из методички (`docs/examples/pzN.md`)
5. **Не хватает данных из методички — сказать об этом.** Не подставлять правдоподобные числа
6. **Новую архитектуру грузить в чистую сессию** ИИ-инструмента. Контекст-загрязнение из старых версий проекта уже происходило: всплывала авторизация из проекта «КСГ», которого в этой архитектуре нет
7. **Документы должны лежать в репозитории**, а не вставляться текстом в чат — иначе `AGENTS.md` не подхватывается, ссылки между документами не резолвятся
8. **Дублировать интерфейсы в артефактах** для визуальной проверки интерактива и адаптивности
