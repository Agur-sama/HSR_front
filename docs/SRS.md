# Техническое задание
## Веб-симулятор практических заданий ВСМ (vsm-simulator.ru)

**Редакция:** 2 (учтены итоги встречи с заказчиком)
**Статус:** рабочая, часть требований помечена как открытая — см. раздел 10

---

### О документе

Настоящее ТЗ — консолидированный документ верхнего уровня. Точные значения и детали реализации хранятся в рабочих файлах репозитория, ТЗ на них ссылается и **не дублирует**, чтобы избежать расхождения версий:

| Что | Где источник правды |
|---|---|
| Точные CSS-значения, образцы компонентов | `docs/design-reference.html` |
| Технические решения по реализации | `docs/architecture.md` |
| Детализация шагов по каждому ПЗ | `docs/pz-specs.md` |
| Тексты интерфейса и правила валидации | `docs/pz1-copy-and-validation.md` |
| Формат отчёта | `docs/pdf-report.md` |
| Тестовые данные из методичек | `docs/examples/` |
| Нерешённое | `docs/open-questions.md` |

Требования пронумерованы для отслеживания. Приоритеты: **О** — обязательное для MVP, **Ж** — желательное, **П** — постMVP.

## 1. Общие сведения

### 1.1. Назначение
Интерактивный веб-симулятор, воспроизводящий 8 практических заданий (ПЗ1–ПЗ8) курса подготовки специалистов высокоскоростных магистралей. Заменяет ручное выполнение заданий во внешних инструментах (Яндекс.Карты, MS Excel) на единую интерактивную среду с автоматической проверкой корректности ввода и генерацией отчёта.

### 1.2. Пользователи
| Роль | Взаимодействие с системой |
|---|---|
| Студент | Единственный активный пользователь. Проходит модули, вводит данные, скачивает отчёт |
| Преподаватель | Не работает в системе. Назначает вариант устно на паре, принимает PDF-отчёты, проверяет вручную |

Учебные команды (5–6 человек) существуют организационно, но **работы выполняются и сдаются индивидуально**. Преподаватель сопоставляет работы участников одной команды между собой при проверке.

### 1.3. Термины
| Термин | Значение |
|---|---|
| Модуль (ПЗ) | Одно практическое задание, самостоятельная единица прохождения |
| Шаг | Элементарный экран внутри фазы «задание» модуля |
| Тип шага (`kind`) | Класс интерфейсного поведения шага, см. 4.3 |
| Мост | JSON-файл, переносящий результаты между модулями |
| Паспорт | Идентифицирующие данные работы: команда, название линии, вариант, дата |
| Вариант | Набор исходных данных, назначаемый преподавателем |
| Корреспонденция | Пара станций (направление перевозки), например А-Б |

## 2. Требования к системе в целом

| ID | Приор. | Требование |
|---|---|---|
| ОТ-1 | О | Система реализуется как клиентское веб-приложение без серверной части. Отсутствуют: база данных, серверная бизнес-логика, аутентификация, роли пользователей |
| ОТ-2 | О | Развёртывание — статическая сборка, раздаваемая веб-сервером (Caddy/Nginx). Единый билд на все 8 модулей |
| ОТ-3 | О | Технологический стек: React 19, TypeScript, Vite, Vitest. Стилизация — CSS с пользовательскими свойствами |
| ОТ-4 | О | Дополнительные библиотеки: MapLibre GL JS (картография), KaTeX (формулы), @react-pdf/renderer (отчёт) |
| ОТ-5 | О | Глобальный менеджер состояния (Redux/Zustand/XState) не применяется. Состояние модуля — React Context |
| ОТ-6 | О | Все расчётные функции выносятся в отдельный слой (`shared/lib`), свободный от React. Расчётная логика в компонентах не допускается |
| ОТ-7 | О | Использование типа `any` не допускается. Неизвестный на момент проектирования тип — `unknown` с явной пометкой |

**Обоснование ОТ-1:** проверка работ выполняется преподавателем вручную по PDF. Учётные записи не решают ни одной задачи процесса, но добавляют стоимость поддержки и требования по защите персональных данных студентов.

## 3. Требования к интеграции с LMS

| ID | Приор. | Требование |
|---|---|---|
| ИТ-1 | О | Каждый модуль встраивается в курс iSpring Suite как отдельный Web Object через `<iframe>` |
| ИТ-2 | О | Все 8 модулей обслуживаются единой сборкой. Выбор модуля — через параметр URL `?pz=N`, где N = 1..8 |
| ИТ-3 | О | При отсутствующем или некорректном значении `pz` система отображает информационную заглушку, не аварийное завершение |
| ИТ-4 | О | Корневой контейнер приложения не создаёт собственной полосы прокрутки (`overflow: hidden`). Прокручиваются только внутренние области (`overflow-y: auto`). Двойная прокрутка не допускается |
| ИТ-5 | О | Интерфейс сохраняет работоспособность при уменьшении контейнера. Порядок деградации: сначала сокращаются вспомогательные элементы (боковые панели, подписи), в последнюю очередь — рабочая область (карта, таблица) |
| ИТ-6 | Ж | Ориентировочный минимальный размер контейнера — 960×540 (соотношение 16:9) |
| ИТ-7 | П | Согласование высоты с контейнером плеера через `ResizeObserver` + `postMessage` — при условии поддержки со стороны iSpring (не подтверждена) |
| ИТ-8 | О | Интерфейс не содержит форм регистрации и входа, глобальных футеров, объёмных шапок |

## 4. Функциональные требования

### 4.1. Жизненный цикл модуля

| ID | Приор. | Требование |
|---|---|---|
| ФТ-1 | О | Модуль состоит из четырёх последовательных фаз: **интро → теория → задание → итог** |
| ФТ-2 | О | Фаза «задание» представляет собой массив шагов переменной длины, не единый экран |
| ФТ-3 | О | Прохождение линейное вперёд. Переход на непройденный шаг в обход предыдущих не допускается |
| ФТ-4 | О | Возврат к ранее пройденным шагам разрешён. При возврате введённые данные сохраняются и доступны для изменения |
| ФТ-5 | О | Фаза «теория» доступна двумя способами: последовательно при первом прохождении и в любой момент как накладываемая панель поверх текущего шага задания. Открытие теории не изменяет текущую фазу и текущий шаг |

### 4.2. Интро и вариантность

| ID | Приор. | Требование |
|---|---|---|
| ФТ-6 | О | На экране интро студент заполняет паспорт работы: название команды, название линии, назначенный вариант |
| ФТ-7 | О | Все поля паспорта обязательны. Переход к следующей фазе блокируется до заполнения |
| ФТ-8 | О | Наборы вариантов хранятся статически в сборке (`variants.ts` модуля). Обращение к внешним источникам не производится |
| ФТ-9 | О | Наличие вариантов не универсально для всех модулей. Подтверждено наличие: ПЗ1 (6 направлений), ПЗ4, ПЗ5, ПЗ6 (по 10 вариантов) |
| ФТ-10 | О | Выбор варианта подставляет **исходные данные**. Ход решения и результат студент выполняет самостоятельно |
| ФТ-11 | Ж | Поля, значения которых поступают из варианта, отображаются в режиме «только чтение» с пояснением происхождения значения |

### 4.3. Типы шагов

| ID | Приор. | Требование |
|---|---|---|
| ФТ-12 | О | Функциональность модулей реализуется через ограниченный набор типов шага. Уникальный интерфейс под каждый модуль не разрабатывается |

Утверждённая таксономия (13 типов):

| `kind` | Назначение | Применяется в |
|---|---|---|
| `data-entry` | Ввод в свободные поля | ПЗ1, ПЗ3, ПЗ4, ПЗ8 |
| `data-entry-hint` | Поле с постоянно отображаемым справочным диапазоном | ПЗ1 (13 показателей), ПЗ3 (калькуляция) |
| `interactive-table-variant` | Таблица «параметр × вариант», назначенный вариант выделен | ПЗ4, ПЗ5, ПЗ6 |
| `interactive-table-matrix` | Симметричная матрица «откуда/куда», диагональ заблокирована | ПЗ1, ПЗ7 |
| `interactive-table-optimizer` | Таблица с пересчётом производных показателей при вводе и цветовой индикацией | ПЗ7 |
| `table-calculator-hybrid` | Таблица, где каждая строка рассчитывается по своей формуле, с итоговой строкой | ПЗ6 |
| `calculator` | Последовательность формул; шаг может использовать результат предыдущего | ПЗ1, ПЗ4, ПЗ5, ПЗ6, ПЗ7 |
| `drag-drop-map` | Картографический интерактив | ПЗ1 |
| `drag-drop-scheme` | Интерактив на подготовленной схематической подложке | ПЗ5 |
| `scheme-reader` | Анализ готовой схемы с последующим расчётом; редактирование схемы не предусмотрено | ПЗ2 |
| `survey-constructor` | Конструктор структуры анкеты | ПЗ8 |
| `control-questions` | Текстовые ответы на вопросы понимания | ПЗ3, ПЗ5, ПЗ7 |
| `schedule-graph` | График движения поездов | ПЗ7 |

Визуальные образцы всех типов — `docs/design-reference.html`.

### 4.4. Обмен данными между модулями (мост)

| ID | Приор. | Требование |
|---|---|---|
| ФТ-13 | О | Результаты модулей накапливаются в едином JSON-файле, а не в отдельных файлах на каждый модуль |
| ФТ-14 | О | Структура файла версионируется полем `schemaVersion` |
| ФТ-15 | О | Данные предыдущих модулей **только предзаполняют** поля последующих. Отсутствие данных не блокирует работу |
| ФТ-16 | О | Каждый модуль сохраняет полную работоспособность при запуске «с чистого листа» — через ручной ввод или выбор варианта |
| ФТ-17 | О | Экспорт файла моста доступен на экране «итог» |
| ФТ-18 | Ж | Импорт файла моста доступен на экране интро модулей, следующих за первым |

**Обоснование ФТ-15/16:** модули проходятся с интервалом до нескольких месяцев, возможно на разных компьютерах. Обязательная передача данных между модулями сделала бы систему неработоспособной при утере файла.

Граф зависимостей (проверен по методичкам):

| Связь | Передаваемые данные | Статус |
|---|---|---|
| ПЗ1 → ПЗ3 | Максимальная скорость участка | Подтверждена текстом методички |
| ПЗ1 → ПЗ7 | Матрица корреспонденций | Подтверждена |
| ПЗ1 → ПЗ2 | Параметры кривых (радиусы) | **Требует подтверждения**, см. 10 |
| ПЗ4, ПЗ5, ПЗ6, ПЗ8 | Только паспорт | Автономны, подтверждено |

### 4.5. Сохранение результатов

| ID | Приор. | Требование |
|---|---|---|
| ФТ-19 | О | На каждом шаге доступна кнопка сохранения результата шага |
| ФТ-20 | О | Экран «итог» отображает **вычисляемую** сводку. Показатели рассчитываются от актуального состояния модуля при каждом отображении |
| ФТ-21 | О | При возврате назад, изменении данных и повторном переходе к итогу результаты пересчитываются. Замороженный снимок результата не сохраняется |
| ФТ-22 | О | На экране «итог» отображается предупреждение о необходимости сохранить файл перед выходом |
| ФТ-23 | — | **Сохранение состояния между сессиями — не определено.** См. раздел 10, требует разрешения конфликта |

## 5. Требования по модулям

Полная детализация шагов — `docs/pz-specs.md`. Ниже — требования, специфичные для модулей.

### 5.1. ПЗ1 — Технико-экономическое обоснование

**Картографический шаг**

| ID | Приор. | Требование |
|---|---|---|
| ПЗ1-1 | О | Карта отображается в двухмерном режиме с топографической подложкой (лес, водные объекты, рельеф отмывкой). Трёхмерный рельеф, наклон камеры не применяются |
| ПЗ1-2 | О | Все подписи на карте — на русском языке. Используются векторные тайлы с полем `name:ru` |
| ПЗ1-3 | О | Поиск населённых пунктов выполняется по статическому набору данных, включённому в сборку. Обращение к внешним геокодерам не производится |
| ПЗ1-4 | О | Система различает **два независимых набора точек**: станции и вершины трассы |
| ПЗ1-5 | О | **Станции**: ровно 2 начально-конечные (А, Г) и не более 2 промежуточных (Б, В). Постановка сверх лимита блокируется с пояснением |
| ПЗ1-6 | О | **Вершины трассы**: количество не ограничено. Предназначены для обхода водных объектов и возвышенностей |
| ПЗ1-7 | О | Линия трассы **не строится автоматически** соединением станций. Геометрия задаётся собственным редактируемым набором вершин |
| ПЗ1-8 | О | Между соседними вершинами задаётся **радиус кривой**. Трасса состоит из прямых вставок и круговых кривых |
| ПЗ1-9 | О | Система рассчитывает длину каждого участка и **общую длину трассы** |
| ПЗ1-10 | О | Линия ВСМ отображается красным цветом и располагается поверх остальных слоёв карты |
| ПЗ1-11 | О | Режимы редактирования разделены: «станция» и «линия трассы» |
| ПЗ1-12 | П | Инструмент выделения регионов прохождения (полигоны) — необходимость не подтверждена, см. 10 |

**Потребительские свойства**

| ID | Приор. | Требование |
|---|---|---|
| ПЗ1-13 | О | Таблицы потребительских свойств формируются **на каждую корреспонденцию** (пару станций). При 4 станциях — 6 наборов: А-Б, А-В, А-Г, Б-В, Б-Г, В-Г |
| ПЗ1-14 | О | Состав каждого набора: время в пути, коэффициент дискомфорта, частота сообщения, средняя стоимость проезда — по видам транспорта |
| ПЗ1-15 | О | Столбец (вид транспорта) может быть удалён, если данный вид сообщения между указанной парой станций отсутствует |
| ПЗ1-16 | О | Коэффициент дискомфорта отображается с цветовой индикацией: значение 0 — зелёный, 1 — красный |

**Расчётная часть**

| ID | Приор. | Требование |
|---|---|---|
| ПЗ1-17 | О | Матрица корреспонденций формируется автоматически из назначенных станций. Размер динамический (2–4 станции) |
| ПЗ1-17а | О | Общее число шагов фазы «задание» модуля ПЗ1 переменно и зависит от числа станций: `3 + 2×C(n,2)`, где n — число станций. Диапазон: 5 шагов (2 станции) … 15 шагов (4 станции) |
| ПЗ1-17б | О | Оценка итогового числа шагов отображается студенту сразу после формирования матрицы корреспонденций, до начала повторяющихся шагов |
| ПЗ1-18 | П | Прогноз пассажиропотока реализуется по модели модального сплита (источник — `docs/examples/pz1-passenger-flow.md`). Для MVP допустима заглушка |
| ПЗ1-19 | О | Блок итоговых показателей содержит 13 позиций. У капиталоёмких показателей отображается справочный диапазон значений |

### 5.2. ПЗ2 — Профиль и план трассы
Анализ готового продольного профиля и плана трассы, определение ограничивающего фактора и максимальной скорости. Формулы — `docs/pz-specs.md`.

### 5.3. ПЗ3 — Выбор ВСП и ИССО
Выполняется для двух участков протяжённостью 10–30 км. Скорость участков поступает из ПЗ1. Включает калькуляцию по 12 статьям расходов и контрольные вопросы.

### 5.4. ПЗ4 — Напряжение плеч питания
Автономный модуль. Вариантная таблица (10 вариантов) и последовательность из трёх расчётных шагов. Контрольный числовой пример — `docs/examples/pz4.md`.

### 5.5. ПЗ5 — Сигнализация и пропускная способность
Два независимых блока. Первый — расстановка сигналов на схеме станции в пять последовательных этапов ограждения. Второй — расчёт пропускной способности по вариантной таблице.

| ID | Приор. | Требование |
|---|---|---|
| ПЗ5-1 | О | Подложка схемы станции подготавливается заранее в векторном формате. Процедурная генерация схем не разрабатывается |
| ПЗ5-2 | О | Допустимые точки размещения сигналов размечаются на подложке заранее, с учётом типа сигнала |

### 5.6. ПЗ6 — Расчёт стойл депо
Автономный модуль. Вариантная таблица, каскадный расчёт программы обслуживания, расчёт числа стойл. Контрольный пример — `docs/examples/pz6.md`.

### 5.7. ПЗ7 — Набор остановок и потребный парк
Два блока. Первый — шахматная таблица пассажиропотоков и оптимизация набора остановок с пятью аналитическими вопросами. Второй — график движения и расчёт потребного парка.

| ID | Приор. | Требование |
|---|---|---|
| ПЗ7-1 | О | Шахматная таблица имеет динамический размер по числу станций, назначенных в ПЗ1 |
| ПЗ7-2 | О | Показатели оптимизации пересчитываются при каждом изменении и сопровождаются цветовой индикацией близости к оптимуму |
| ПЗ7-3 | — | Механика увязки поездов по станциям оборота — не определена, см. 10 |

### 5.8. ПЗ8 — Обслуживание пассажиров
Конструктор структуры анкеты и анализ результатов опроса.

| ID | Приор. | Требование |
|---|---|---|
| ПЗ8-1 | — | Способ сбора ответов респондентов не определён. Проведение опроса внутри системы невозможно при отсутствии серверной части (ОТ-1). См. 10 |

## 6. Требования к пользовательскому интерфейсу

### 6.1. Визуальное оформление

## 10. Открытые вопросы

Требования, не подлежащие реализации до получения решения. Ведение — `docs/open-questions.md`.

### 10.1. Требует разрешения внутри команды

**Сохранение состояния между сессиями (ФТ-23).** Предложены три несовместимых подхода: локальное хранилище браузера, только файл обмена, загрузка по идентификатору. Третий вариант противоречит ОТ-1 (отсутствие серверной части) и требует пересмотра архитектуры в целом. До принятия решения реализуется работа без сохранения между сессиями, с предупреждением пользователя (ФТ-22).

## 11. Вне объёма работ

Явно не реализуется:

- Учётные записи, роли, разграничение доступа
- Интерфейс преподавателя, автоматическая проверка работ, журнал успеваемости
- Совместная работа в реальном времени, синхронизация между участниками команды
- Хранение работ на сервере
- Мобильная версия (система рассчитана на работу в аудитории на стационарной технике)
- Процедурная генерация схем станций
- Перенос методических материалов в систему целиком — используется краткое изложение с возможностью открыть исходный документ
